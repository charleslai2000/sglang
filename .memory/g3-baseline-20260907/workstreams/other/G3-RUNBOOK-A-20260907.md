## 3. Endpoint/backend binding and rationale

**Backend decision: `--backend sglang`** (native SGLang `/generate`).

- The laid-out `run-production-A.sh` from the prior interrupted dispatch (`/data/qwen3-g3-baseline/production-A-20260907/G3-PRODUCTION-A-20260907T100230Z/run-production-A.sh`) used `--backend sglang`, `--base-url http://127.0.0.1:8035`, `--dataset-name random`, `--random-input-len 2048 --random-output-len 512 --random-range-ratio 1.0 --request-rate inf --seed 42 --max-concurrency <C> --num-prompts <N> --output-details --output-file <...>/result.jsonl --flush-cache --flush-cache-timeout 60 --warmup-requests 3` — no `--tag`. Both prior-halt runs (T100230Z, T101034Z) were OOM-killed at C1 (rc 137) **before** the API phase; their bindings still establish the intended production-A convention.
- **Claim (with evidence)**: the production v1 service is OAI-API-compatible and the chat-style probe `POST /v1/chat/completions` returned `pong`. The native `sglang` backend avoids OpenAI-format re-tokenization of the already-tokenized fixed-length prompts and hits `/generate`. Because **the protocol's unit is the unchanged production service**, the benchmark must exercise the identical service code path that productions serve — here that is the native `/generate` path (the service is launched with `sglang serve`, which implements `/generate` as its native endpoint). The OAI chat-completions path is an additional compatibility layer; measuring it would measure the wrapper, not the engine's served path, and would not satisfy "identical pre/post MMQ" reproduction (the MMQ patch cannot alter the OAI wrapper without leaving the delivered path).
- **Consequence**: with `--backend sglang`, the runner posts only `POST /generate` during warmup and measurement (server mutation), plus `POST /flush_cache?timeout=60` at flush. There is **no other server mutation** the explicit invocation performs; in particular `GET /v1/models`/`GET /model_info`/`GET /health`/`GET /v1/loads` are read-only and `--served-model-name`/`--extra-request-body` are NOT passed (so no served-name mutation, no `return_cached_tokens_details`).

## 4. Dataset binding (`random`) — D2 conflict surfaced, decision required

Runner truth (Section 0 items 7-8, 13):

- `ratio=1.0` is implemented as exact fixed len (verified). Prompt-content distribution is still non-deterministic in the `random` path even at ratio 1.0 (sample-then-recycle ShareGPT text).
- `dataset_name=random-ids` → `random_sample=False` → fully deterministic (seed 42) random-integer token IDs, decode to text once. Numeric-only text is not "natural language," but it is **fixed-length, seed-deterministic, no network**. Pre/Post MMQ identical input is guaranteed because the runner's `random-ids` generator is deterministic (verified source). `num_special_tokens_to_add=0` → no special-token truncation, so the server receives exactly 2048/512 tokens.
- Verified: at seed 42, `random-ids` produces full 2048-token prompts with all positions present and request-distinct content (each request uses a distinct base offset), so Mamba slot occupancy is equivalent to any real fixed-length prompt and is fully deterministic pre/post. The only caveat is that prompt text is uniform-random-integer tokens rather than natural-language subsamples (the `random`/ShareGPT path cannot be byte-identical pre/post without an immutable staged file, which this task cannot create).

**No frozen parameter is relaxed here.** The frozen protocol says dataset `random`; the runner requires ShareGPT for `random`. Two faithful bindings are offered to the orchestrator/user:
