## Defects / blockers

1. **CONTROL-PLANE COLLISION (primary blocker; external, reproducible).** Sibling agent tasks
   dispatched from the same orchestrator session are concurrently operating the same GPU, canonical
   lock, and :30000. During this invocation:
   - At **23:47:29** a sibling (`start.sh prod`, parent `1644932` = the shared opencode process)
     started production while my cell-64 load was in flight; my subsequent retry correctly refused
     with `GPU has a material compute holder`.
   - At **23:47:06** and **23:52:~** my cell-64 `load.py` clients received external `SIGTERM`
     (`load_rc=143`, "Terminated"); the same load script completed cleanly for cells 48 and 56, so
     the terminations were external, not load failures.
   - Sibling artifacts on disk document the race directly: `P2-ABORT-SWEEP-AND-START-PROD`,
     `P3-PROD-START-WITH-APPROVAL`, `P4-PROD-RESTORE-AND-HOLD` ("KILLED-AGAIN"), and
     `P5-MAMBA-FINAL-AND-PROD-START`. Sibling `P4` explicitly records an identity-checked kill of a
     production instance and a sweep relaunch; sibling `P5` ran the identical sweep using **my**
     `run_cell.sh`/`cell_supervise.sh` and records that its own cell was SIGTERM'd mid-load.
   - At terminal write a **newer** sibling (`P6`, `/tmp/opencode/p6-mamba-20260918/`) holds the
     canonical lock (`generation 18`) running a "corrected" sweep and owns the production restore.
   Production was cycled between 23:47 and 23:57 by these sibling tasks (instances
   `prod-20260917T234749Z-1733936` at 23:50:01 and `prod-20260917T235414Z-1738571` at 23:56:27 were
   each observed ready, then stopped ~3 s later), so **the restore objective is not establishable
   from this invocation** while the race continues. Per the executor contract I did not signal the
   incumbent, did not launch a second server, and did not duplicate the sibling's active work.
2. **Failure-mode mismatch (measurement defect).** The completed cells produced **only**
   `WAIT_CAPACITY reason=FRONTIER` (an ordering/ACK wait) and **zero** `HOST_ALLOC` /
   `failed_domains=["mamba"]` records, whereas production's tail is `HOST_ALLOC` with mamba host
   aux `free=0` and `required_aux_units={"mamba":3436..3556}`. The sweep therefore did **not**
   exercise the production failure path; the 48-vs-56 result cannot validate a
   `--max-mamba-cache-size` change against that defect. (Confirmed independently by the read-only
   sibling assessment `MAMBA-SWEEP-EVIDENCE-ASSESS-20260918`.)
3. **Cell 64 never completed.** No `cell-64.json`; all attempts terminated by (1). The 3-point
   curve does not exist.
4. **`mamba_available_tokens` is not a clean discriminator.** `pool_stats_observer.py:244-269`
   defines it as `mamba_allocator.available_size()` = *schedulable* free slots, excluding evictable
   (radix-cached) slots; it reads 0 at both 48 and 56 while `mamba_used` plateaus at 32. The device
   pool was never the binding domain, so the flag's device-size axis is not the lever on the
   measured production defect; the plausible channel is the mamba **host (L2)** pool, which is
   split from `--hicache-size` (7.31 GB at 48 -> 8.19 GB at 56, at the cost of ~54k KV-host tokens).
