# DBG-20260908-T38C — S=25 T38C storage-hit causal report

## Invocation

- Task / epoch: `DBG-20260908-T38C` / `2026-09-08`.
- Scope observed: read-only inspection of active worktree cache/storage code and
  the designated 24052 evidence (`/root/evidence-gate3-parked/s25-durable-settle-t38c`,
  `/tmp/t38c-probe.log`). No product or control-plane files were changed.
- Status: **done**.

## Conclusion

The observed `extra_pool_hit_pages={"kv": 55145}` is **not** a successful
sidecar result.  It is the raw, contiguous attention-KV prefix discovered before
the auxiliary-pool fold.  The active extent backend then folds the usable prefix
with `min(final_pages, boundary)` for each auxiliary transfer.  For the T38C
Mamba model, the only such transfer is the Mamba checkpoint transfer.  Its
TRAILING_PAGES scan returns `boundary=0`; therefore the returned
`kv_hit_pages` is zero and the scheduler revokes the prefetch as a full miss.

Thus the direct cause of the zero is **the Mamba trailing-checkpoint input to
the generic `batch_exists_v2` fold**, not loss of the direct KV pages and not an
ALL_PAGES-policy fallback.  The generic fold is operating as designed: it must
not declare an attention-KV prefix restorable without the recurrent state needed
to continue it.

The evidence does **not** yet distinguish these two sub-causes of the zero
Mamba boundary:

1. no Mamba checkpoint was persisted for any hash in the 55,145-token raw-KV
   prefix; or
2. checkpoint data was persisted, but under a hash/seed chain that does not
   equal the read-side hash chain.

That distinction needs one targeted per-transfer/key probe; it must not be
papered over by accepting KV-only restores or changing the `min` fold.

## Reconstructed timeline and reproduction evidence

1. The authoritative ledger records the earlier S=100 failure after a tokenizer
   comparison: cold and warm requests shared a 55,145-token prefix, while
   warm turns still had `extent_read=0` and `restore_ready=0`
   (`.memory/phase2-hicache-design/ledger.md:2811-2825`).  This rules out the
   chat-template/assistant-state hypothesis for this later diagnostic shape.
2. T38C is the S=25 durable-settle run.  Its live probe has 36
   `pc_storage_query` events.  Representative warm queries repeatedly report
   `query_suffix_len=55425`, `kv_hit_pages=0`, `storage_hit_count=0`, and
   `sidecar_hits={"kv":55145}`; later the same pattern occurs at
   `query_suffix_len=55426` with raw KV `55146`
   (`/tmp/t38c-probe.log`, events at timestamps 1788798820.941,
   1788798858.381, 1788798895.204, and 1788799010.301).
3. The direct-prefix witness is stable across independent warm requests, while
   the usable result is always zero.  This establishes a real L3-resident KV
   prefix followed by deterministic collapse before any data transfer or
   scheduler admission decision.  It is incompatible with a pure KV-key or
   generic storage-absence explanation.
4. The probe outcome path turns that zero into `revoked_full_miss`, so the
   externally visible recomputation follows the query result rather than
   causing it.

## Code-level causal chain

### 1. Mamba is the only auxiliary state in this deployed model shape

- `_MambaStrategy.matches` requires FULL + MAMBA, and its build result registers
  those two host pools only; it returns no generic sidecar specs
  (`python/sglang/srt/mem_cache/hybrid_cache/hybrid_pool_assembler.py:1266-1318`).
- The active launch uses Qwen3.5 with `--mamba-radix-cache-strategy extra_buffer`
  and no speculative/draft-model argument (captured in the T38C run command).
  Consequently draft/DeepSeek sidecars are not a competing auxiliary transfer.
- During prefetch, the Mamba component creates exactly one host staging transfer
  named `PoolName.MAMBA`, with placeholder key and
  `PoolHitPolicy.TRAILING_PAGES`
  (`python/sglang/srt/mem_cache/unified_cache/components/mamba_component.py:765-774`).

### 2. The direct KV measurement is retained in the misleadingly named map

- `PoolTransferResult` has separate `kv_hit_pages` and
  `extra_pool_hit_pages` fields
  (`python/sglang/srt/mem_cache/hicache_storage.py:127-147`).
- The extent implementation first finds the raw contiguous KV prefix
  (`kv_pages`), then seeds `hit_count` with `{PoolName.KV: kv_pages}` before
  processing auxiliary transfers
  (`python/sglang/srt/mem_cache/storage/extent/extent_file_backend.py:640-645`).
  It returns this map as `extra_pool_hit_pages` even though its `KV` entry is
  the pre-fold direct-KV observation.
- This representation is intentional and already pinned by a unit assertion:
  a missing component makes final `kv_hit_pages == 0` while
  `extra_pool_hit_pages[PoolName.KV] == 3`
  (`test/registered/unit/mem_cache/test_extent_file_backend_unit.py:585-601`).
  Therefore the T38C label `sidecar_hits["kv"]` is diagnostic naming noise,
  not evidence of a sidecar named KV.
- `HybridCacheController._storage_hit_query` logs precisely that returned map
  under the label `sidecar_hits`, then uses only `hit_result.kv_hit_pages` to
  return the fetchable hash prefix
  (`python/sglang/srt/mem_cache/hybrid_cache/hybrid_cache_controller.py:601-637`).

### 3. Mamba trailing-state failure clamps the raw KV prefix to zero

- For every transfer, the extent backend calculates a transfer boundary.  For
  trailing state it reverse-scans the raw-KV range, looking for the required
  component key(s) at the end of a candidate prefix
  (`extent_file_backend.py:671-680`).  It adds a component entry only for a
  nonzero boundary, then executes `final_pages = min(final_pages, boundary)`
  (`extent_file_backend.py:681-684`).
- The placeholder path is explicitly forced through that trailing scan even if
  a transfer reconstruction had defaulted the policy to ALL_PAGES
  (`extent_file_backend.py:650-671`).  Thus this run is **not** explained by
  a lost `PoolHitPolicy.TRAILING_PAGES` value.
- With raw KV 55,145 and final hit zero, the Mamba scan found no valid endpoint
  anywhere in that raw range (`boundary=0`).  The backend intentionally omits
  the Mamba map entry at boundary zero, explaining why T38C prints only
  `{"kv":55145}` rather than an explicit `"mamba":0`.
- The Mamba write contract uses `keys=[node.hash_value[-1]]`, also marked
  TRAILING_PAGES (`mamba_component.py:752-763`).  Therefore a valid repair
  must make at least one persisted Mamba checkpoint key coincide with the
  read-side raw-KV hash chain; it is not correct to make Mamba an ALL_PAGES
  pool or to ignore it.

### 4. Zero is consumed as an L3 full miss

- `prefetch_from_storage` passes the Mamba transfer as an extra pool to the
  controller (`unified_radix_cache.py:2735-2763,2793-2801`).
- The controller invokes `batch_exists_v2`, stores only the folded result as
  `operation.storage_hit_count`, and returns a prefix truncated to that count
  (`hybrid_cache_controller.py:601-637`).
- The drain path classifies any result below the prefetch threshold, including
  zero, as `revoked_full_miss` and calls `revoke_pending_prefetch`
  (`unified_radix_cache.py:3660-3675`).  This matches the T38C probe chronology.

## Competing hypotheses

| Hypothesis | Verdict | Evidence |
| --- | --- | --- |
| Warm payload / chat template changed the prefix | Ruled out | Ledger tokenizer comparison found a 55,145-token common prefix; T38C independently has a stable raw KV witness of the same order. |
| Direct KV pages are absent from L3 | Ruled out | The backend's raw-KV entry is 55,145/55,146 across warm queries; the exact unit contract shows that this is retained even when the folded result is zero. |
| Generic `batch_exists_v2` accidentally applies ALL_PAGES to a placeholder Mamba transfer | Ruled out | The deployed extent code detects placeholders and executes the trailing scan regardless of a defaulted ALL_PAGES policy. |
| Generic `batch_exists_v2` is the functional fault | Ruled out as root cause | It is the required all-state fold.  It correctly refuses a state-incomplete hybrid restore; bypassing it would corrupt recurrent-state semantics. |
| Mamba trailing checkpoint has no matching key in the raw prefix | Ruled in (direct cause) | Mamba is the only auxiliary transfer for this model, and the raw KV witness is reduced to zero only by its zero trailing boundary. |
| Mamba checkpoint was never written versus written under another hash chain | Open | Existing logs establish neither the queried terminal hash nor per-key Mamba write/lookup presence. |

## Minimal coder fix contract

Do **not** change the generic min-fold, lower the hit threshold, or permit a
KV-only restore for this model.

1. Preserve the existing Mamba semantics: every recoverable attention-KV
   prefix must have a Mamba state checkpoint at a hash in that same prefix;
   Mamba remains `TRAILING_PAGES` and the final usable prefix remains the
   KV/Mamba intersection.
2. Add a narrowly gated structured trace at the extent `batch_exists_v2`
   boundary (or equivalent test hook) that records, for each transfer:
   `name`, `hit_policy`, placeholder status, raw `kv_pages`, resolved boundary,
   and the attempted trailing hash(es).  Pair it with the Mamba storage-write
   acknowledgement: `node_id`, exact write hash, and success/failure.  Do not
   log token text or state bytes.
3. Use that trace in one S=25 cold-build/warm-turn reproduction to choose the
   smallest repair:
   - If no successful Mamba write corresponds to a raw-KV endpoint, fix the
     Mamba persistence scheduling/eligibility so the node’s state is written
     before marking its KV chain storage-durable.
   - If a successful Mamba write exists under a different hash, make the
     backup key use the same page-aligned hash convention and seed as
     `_storage_hit_query`/`get_hash_str`.
4. Add tests at two levels:
   - Extent regression: raw KV length 55,145 plus a Mamba checkpoint at a
     trailing/raw-prefix hash returns that nonzero boundary; no matching
     checkpoint returns zero and retains the raw KV witness.
   - Mamba L3 integration: cold 55K build, wait for both KV and Mamba write
     acknowledgements, evict, then warm request with the same prefix.  Require
     nonzero `storage_hit_count`, a Mamba `batch_get_v2` success, no
     `revoked_full_miss`, and correct continuation output.  Include a negative
     unmatched-tail case that must still reject the restore.

## Followups

- Have the implementation owner collect the paired write/query keyed trace;
  this is the only missing evidence needed to identify whether the defect is
  Mamba write omission or hash-chain mismatch.
- Improve the probe field name from `sidecar_hits` to something such as
  `raw_and_aux_boundaries`, or log raw KV separately, to avoid treating
  `extra_pool_hit_pages[KV]` as a successful sidecar.
