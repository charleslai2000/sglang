## 1. Objective and outcome

Bring up the SGLang HiCache/Ready-Horizon server on the local RTX 3090 for the
Qwen3.5-4B GPTQ model and freeze its exact profile as the P0-B HOST_ALLOC
liveness target.

**Outcome: BLOCKED.** The server process reaches full application startup and
listens on `127.0.0.1:30000`, but the **first (warmup) forward pass deadlocks**
and no generation can complete. Two independent hard blockers were isolated
with raw evidence:

1. **CUDA-graph capture deadlock (original R60 profile).** With the frozen R60
   graph settings (`--cuda-graph-backend-prefill breakable`,
   `--cuda-graph-backend-decode full`), the first graph-captured forward never
   proceeds: the log freezes at `Capture target prefill CUDA graph begin`, all
   worker threads are in `futex_do_wait`, and GPU utilisation is 0%. This
   reproduces deterministically (attempts 1, 2, 3, 4). Disabling prefill graphs
   merely moves the hang to decode graph capture (attempt 4), so it is the
   first captured forward, not a phase.
2. **HiCache host-memory shortfall (fully eager).** With all CUDA graphs
   disabled (attempt 5), startup proceeds and then dies in HiCache init:
   `ValueError: Not enough host memory available. Requesting 15.20 GB but only
   have 7.85 GB free.` Root cause: `host_memory_budget = psutil.available - 10
   GB` and `hicache-ratio 2.0` doubled the auto-scaled 147-state mamba device
   pool into a 15.2 GB host pool. Capping `--max-mamba-cache-size 53` (attempt 6)
   fixed this: host KV pool 2.15 GB + host mamba pool 5.51 GB allocated, server
   started.
3. **Forward-pass deadlock remains (attempt 6).** After the fixes above the
   server starts, `/model_info` returns 200, but `/health` stays 503 and the
   warmup request admitted at 21:06:50 never completes. A fresh
   `/v1/chat/completions` request timed out (HTTP 000 after 75 s); all 46 worker
   threads are in `futex_do_wait`, GPU 0% at 8.8 GiB held. So the deadlock is in
   the forward path itself, independent of CUDA graphs and of host capacity.

The server was **stopped** (it was hung and holding the 3090). Nothing is left
running. No repo file was modified by this task.

## 9. Smallest fix hypotheses (not executed; need orchestrator/owner authority)

Ordered by cost, all confined to isolating the **forward-pass deadlock** (the
dominant blocker; blockers 1 and 2 are understood and have working settings):

1. **Repo-revision isolation.** The R60 frozen profile is known-good at commit
   `9213ee0`; the local tree is 3 RH commits ahead (`4f41f5b`). Run the same
   attempt-6 command against `9213ee0`. If it serves, bisect
   `a96dc148c2`, `1a8879750d`, `03a170ef4f`, `9213ee01d9` (all RH
   telemetry/scheduler paths). Requires checkout authority — `Do NOT edit repo
   files` was in force here.
2. **Quantization isolation.** The R60 known-good vehicle was AWQ
   (`awq_marlin`); this is GPTQ (`gptq_marlin`), and the loader emits repeated
   `Parameter model.layers.N.linear_attn.in_proj_ba.weight not found in
   params_dict`. Test the same command against a local AWQ/GPTQ twin to decide
   whether gptq_marlin or the checkpoint is the trigger.
3. **Kernel-path isolation.** The hang is in the first GDN forward
   (`TritonGDNKernel`, `packed_decode=True`) on SM86. The repo carries a GDC/PDL
   SM86 guard history (`review/gates/P0-3060-SM86-GDC.md`) and `--linear-attn-*`
   backends exist; determine whether a different linear-attn backend avoids the
   deadlock. Product/diagnosis work, not an executor change.
4. **Attach a debugger for a Python traceback.** `gdb -p` is blocked here
   (`kernel.yama.ptrace_scope=1`, no sudo), so no Python stack could be
   captured. A run with `ptrace` permitted (or `py-spy`, not installed) would
   give the exact frame.
