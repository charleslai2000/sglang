## Can existing telemetry close the chain?

### Conditional answer: yes for observation, no with existing vehicles

The current schemas contain enough dimensions to prove the chain **without new product instrumentation**, provided one bounded current-revision run emits all mandatory values and the mutation sample containing each required blocked-domain generation edge is present:

`complete lifecycle context on wait -> cache instance + captured per-pool generations -> exact mutation edge(s) for that cache/pool -> wake current generation/vector + FIFO grant -> same RID/attempt retry -> full per-pool allocation result -> accepted all-or-nothing hybrid finalization -> same RID/attempt READY`.

The physical release event does not need to be caused by the waiting request. It must instead be joined to the wait/wake as the authoritative mutation of the **same cache instance, blocked pool, and exact generation edge**. A non-null `causal_rid` is desirable when there is a causal requester, but it is not a substitute for — or necessarily part of — the allocator transition identity. The reducer must reject a generation jump whose intervening raw mutation row is absent.

This conclusion is conditional because mutation telemetry is bounded/sampled (`unified_radix_cache.py:149-158,3723-3735`), trace context is marker-gated, and the only inspected live log (R32) lacked context. No read-only analysis can establish that a future run will emit a complete sample.

Existing vehicles still cannot close the chain because none:

- deterministically stages one singular full KV+Mamba storage hit into a real host-capacity denial;
- creates a bounded external holder/release sequence through documented interfaces;
- consumes both `p0_durable.v3` and `host_alloc.v1` while preserving their raw references;
- validates exact generation edges, FIFO predecessor ordering, one retry, no crop/fallback/discard, and authoritative READY.

## Exact identity and correlation contract

These are not proposals for synthetic fields. Every value must be product-emitted or established through a documented request interface and then retained unchanged.

### Mandatory singular lifecycle identity

- `run_id`
- `session_id`
- `session_generation`
- `build_rid`
- `node_id`
- `final_kv_hash`
- warm/request `rid` (including the warm RID where distinct)
- HOST_ALLOC restore `attempt_id`
- `cache_instance_id`
- worker/rank identity

### Mandatory allocation correlation

- positive full KV hit tokens and all required Mamba/aux sidecar pages/keys;
- requested primary token span and every required auxiliary unit count;
- blocked domains;
- waiter's captured per-pool generations, free units, and evictable units;
- waiter `fifo_sequence`, plus enough competing-waiter records to prove no earlier eligible waiter was skipped;
- mutation pool, exact generation before/after, cause, returned units, evictable before/after, cache instance, and monotonic telemetry sequence;
- wake current generations and generation-vector ID, decision, fit snapshot, and grant/skip reason;
- exactly one retry attempt ID, preserved through retry result, hybrid finalization, and READY;
- per-pool first allocation, bounded reclaim, second allocation, and post-state;
- full frontier size, `crop_attempted=false`, `lower_checkpoint_queried=false`, `genuine_miss=false`;
- complete KV expected/fetched values, every sidecar expected/fetched count, `all_or_nothing=true`, accepted finalization, and explicit READY.

### Fields absent or unusable in the R32 live evidence

- HAE mutation `rid`, `attempt_id`, `causal_rid`, and `trace_context` were null.
- RH request `session_generation` was null.
- No authoritative six-field lifecycle tuple was retained across HOST_ALLOC wait, mutation, retry, finalization, and READY.
- No parked wait record, captured blocked-domain generation cursor, FIFO ticket/grant, same-attempt retry result, accepted hybrid finalization, or correlated READY existed for one singular lifecycle.

### Current schema seams a reducer must bridge, without manufacturing data

- `p0_durable.v3` carries lifecycle identity; `host_alloc.v1` carries HOST_ALLOC mechanics. Existing reducers accept only one side.
- `ready_host` is text telemetry with RID/attempt and completion data but does not itself repeat the six lifecycle fields or cache-generation cursor. The join is valid only if a preceding HAE record on the exact RID/attempt has complete context; otherwise fail closed.
- `host_allocability_change` may legitimately have null request identity because capacity release can be global. It must be joined only by exact cache instance, pool, and contiguous generation edge bounded by the captured/current cursor — never by timestamp alone.
- If any required trace context, exact mutation edge, or READY attempt lineage is absent, the result is `NOT_VERIFIED`; the reducer must not backfill it from client timing or nearby rows.

## Smallest authorized architecture after user approval

### Component 1: temporary external workload driver

Ownership is limited to stimulation through documented public interfaces:

1. create one build/session with complete lifecycle identity and a positive full KV+Mamba durable artifact;
2. consume host capacity with a bounded, predeclared number of ordinary requests until the target warm request is not allocable and parks;
3. release exactly one predeclared holder through a documented client/lifecycle action;
4. wait for product-owned scheduler/allocator behavior; never select, wake, retry, or declare READY itself;
5. stop on timeout, unexpected process state, resource bound, or more than one target retry.

No product imports, monkeypatches, callbacks, internal scheduler calls, direct allocator calls, process-memory access, or synthetic event emission are permitted.

### Component 2: temporary offline fail-closed reducer

It consumes immutable raw server/event logs after the bounded run. It performs exact-key and exact-generation joins, preserves raw line references, and emits only `VERIFIED` or `NOT_VERIFIED` with reasons. It owns no runtime control. Its acceptance predicate is all of the mandatory legs above, including negative checks for genuine miss, crop, lower-frontier substitution, same-generation self-wake, repeated retry, skipped eligible FIFO predecessor, partial sidecar, discarded hybrid, recompute fallback, and READY before finalization.

The output bundle should contain manifest/provenance, exact command transcript, raw logs, request/response records, normalized ordered trace with raw references, verdict, pre/post safety state, cleanup record, and SHA256 checksums.

### Review and execution sequence

1. User authorization.
2. Fresh implementation dispatch with exact two-file write set in an isolated local directory.
3. Independent code/security/scope review and immutable hashes.
4. Fresh 3060-only execution dispatch; no 3090/production use.
5. Fresh independent evidence review. P0-B closes only on that review's acceptance.

## Assumptions and uncertainty

- **Observed:** current source defines richer request-correlated HAE records than the R32 runtime captured.
- **Assumption:** the future authorized 3060 checkout will be hash-aligned with these source paths and the marker-gated lifecycle context can be enabled through an already-existing reviewed mechanism. Execution preflight must verify this; do not assume it from local source.
- **Uncertainty:** bounded mutation sampling may omit an exact edge if the run is noisy. The reducer must reject gaps. Changing sampling is instrumentation, not an execution tweak.
- **Uncertainty:** a public-interface-only pressure/release sequence may not deterministically produce the desired hybrid allocation shape. The harness may bound and attempt the scenario, but may not reach into allocator internals to force it.
- **Uncertainty:** proving “exactly one eligible FIFO retry” with only one waiter proves single retry but gives weak evidence of predecessor ordering. The preferred bounded scenario includes one controlled predecessor or otherwise captures the full waiter queue evidence already emitted; the harness must not redefine FIFO semantics.
