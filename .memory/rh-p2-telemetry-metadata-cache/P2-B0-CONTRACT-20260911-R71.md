## Q1 — Do `C1/C4/C5/C6/C8` mean concurrency levels or legacy ratio tiers?

**Resolved: concurrency levels.** [E]

Evidence:

1. `plan.md:18` calls `C1/C4/C5/C6/C8` the 主矩阵 ("main matrix") and says `C2` is
   sanity-only. `plan.md:104` calls the same set "C1/C4/C5/C6/C8 主矩阵及规定的
   **concurrency/capacity matrix**".
2. The measured 3060 sweep is explicitly nominal concurrency `c1/c2/c4/c6/c8`
   (`OPS3060-DECODE-CONCURRENCY-SWEEP-R1-20260910.md:11`, table `:16-22`), with the
   per-request decode rate roughly constant and aggregate throughput scaling with
   concurrency (`:24-27`).
3. The mamba-ratio tier scheme uses the **capital** `C0..C5` for
   `--mamba-full-memory-ratio` candidates (`phase2-cap-protocol-architect-e1.md:108-117`),
   and that scheme belongs to the 3090 line, which is out of scope for the 3060 product
   (`plan.md:3`).

Decisive disambiguation (the collision cannot be read as ratio tiers):

- The ratio-tier table has **no** `C6` or `C8`; the main matrix requires both.
- Under the ratio reading, `C2` = ratio 0.45 would be a first-class sweep member, but
  `plan.md:18` / `ledger.md:4591` explicitly place `C2` outside the main matrix as
  sanity-only.
- Ratio tiers C4/C5 denote ratios 0.25 / (0.40|0.30) (`phase2-cap-protocol-architect-e1.md:113-115`),
  which have no relation to the 3060 concurrency rows.

**Frozen naming rule (proposal):** `C<n>` = nominal client **concurrency level** n in
the P2-B main matrix. Never use `C<n>` for a ratio. If a ratio dimension is ever needed,
name it `R<ratio>` (e.g. `R0.33`). [I for the naming rule; E for the meaning]

Secondary semantics to freeze:

- "Nominal concurrency" = number of concurrently offered request streams
  (driver agents = C<n>; engine `--max-running-requests = C<n>`).
- "Effective concurrency" = observed `max(num_running_reqs)` per cell; if the engine
  caps below nominal (mamba-slot cap), report actual and flag the cell. [E for the cap
  mechanism, `phase2-hicache-design-tester-decbm-e1.md:36-45`; I for mandating both
  numbers in every row]
- `C2` is **excluded** from the main matrix, gain table, gates, capacity policy, and
  merged throughput conclusions; it may appear only under `OUT-C2` marked `sanity-only`.
  `C5` has **no measured 3060 baseline** (`HANDOFF-...-48H-SUMMARY.md:69`; `context.md:28`),

### 3.2 Scenario classification and TTFT

| Scenario | Definition |
|---|---|
| `L1-hit` | Request satisfied from device KV with no host/L3 restore needed. |
| `L2-restore` | Request satisfied by a host-resident (L2) restore; storage contribution 0. |
| `RH-staged-L3` | L3-backed request already staged by RH to Host-ready before admission. |

### 3.3 `cache-induced idle` — definition and measurement

Semantic definition (frozen, user wording): GPU idle time while runnable work exists
because cache/state is not ready. [E]

Proposed normative measurement contract [I]:

- Report as **duration (seconds) and as a fraction of the measurement window**.
- Requires two inputs: (i) a request state classifier marking "runnable but not
  computable because cache/state is not ready"; (ii) a GPU busy/idle timeline at a
  resolution fine enough to locate idle intervals (5 s `nvidia-smi` sampling is *not*
  sufficient — see `OPS3060-DECODE-CONCURRENCY-SWEEP-R1-20260910.md:35-36`, "samples,
  not peak measurements").
- `cache-induced idle` is a **GPU-timeline** metric, not a sum of per-request waits;
  the four per-request terms are the reconciliation evidence. The two must be reported
  together with an explicit reconciliation residual, not forced to be equal.
- If either input is unavailable, emit `not computable` with the missing input named.

### 3.4 Four-term split — semantics, formula, and computability

Frozen semantics (mutually exclusive, per request, in request-resident order) [I]:

| Term | Semantic boundary | Formula (proposed) | Current computability |
|---|---|---|---|
| `restore_wait` | Runnable request blocked because its KV/state is not resident/ready (cache-induced wait: L3→L2 staging, Host-ready, WAIT_CAPACITY, capacity retry). | `t(admission_ready) − t(entered_cache_wait)` | **not computable** — no `WAIT_CAPACITY` enter/exit duration field; state machine is timestamp-free in `hicache_restore.py`; existing timestamped events cannot bound a full wait interval by RID. |
| `queue_wait` | Runnable and cache-ready request waiting for scheduler admission (queue position / token budget), excluding `restore_wait`. | `t(admitted) − t(cache_ready)` | **not computable** — no request enqueue timestamp; `sglang:encoder_queue_wait_seconds` (`metrics_collector.py:2442-2501`) is encoder-scoped, not this path. `evt=admission` (`scheduler.py:6229`) has a timestamp but no matching enqueue mark. |
| `compute` | GPU prefill/forward compute attributable to the request. | `Σ(prefill forward interval)` | **not computable** — no per-request prefill duration/first-token field found in `scheduler.py`. |
| `decode` | GPU autoregressive decode attributable to the request. | `t(finish) − t(first_token)` (client, streaming) | **computable only with true streaming TTFT**; cannot add decode time from non-streaming wall. |

Invariants and rules (proposal) [I]:

1. The four terms MUST be non-overlapping per request; a term that cannot be measured is
   `not computable`, **never 0** (`plan.md:16`).
2. Per-request coverage invariant (diagnostic, tolerance-based):
   `restore_wait + queue_wait + compute + decode ≈ request latency` (excluding
   transport). Report the residual; do not silently absorb it.
3. `cache-induced idle` reconciliation: report
   `cache-induced idle` alongside `restore_wait`, `queue_wait`, `compute`, `decode`
   with an explicit reconciliation residual. A non-zero residual is a reported fact,
   not a gate failure.
4. The existing `load_back_duration_seconds` histogram
   (`metrics_collector.py:2236-2307`) is a whole-operation timer and MUST NOT be used as
   isolated `restore_wait` (`plan.md:78`). [E]
5. The engine already emits timestamped RH events (`rh_match_prepare.v1`,
   `rh_stage.v2`, `ready_host`, `admission.v2`, `frontier_wait`, `admission`) but R63
   found no single identity-complete record and R65 found no duration field; timestamp
   pairs are therefore not a substitute for a defined `WAIT_CAPACITY` enter/exit seam. [E]

## Frozen contract proposal (v0.1-proposal)

Normative rules, to be frozen after the three open decisions are ratified.

1. **Scenario/C-labels.** `C1/C4/C5/C6/C8` are nominal concurrency levels; `C2` is
   sanity-only (out of matrix). `R<ratio>` denotes ratio dimensions and is unused here.
2. **Scenarios.** L1-hit, L2-restore, RH-staged-L3, cold-L3, as defined in §3.2.
   TTFT P95 per scenario from real streaming first-token timestamps; cold-L3 exempt
   from `<1s`.
3. **Throughput fields (six).** Each carries an explicit numerator/denominator/window:
   - `aggregate_output_tps` = Σ output tokens / window. [E]
   - `input_compute_tps` = Σ prefill-compute tokens / window. [E]
   - `request_throughput` = Σ completed requests / window (completion set defined). [I]
   - `completed_tasks_per_gpu_hour` = Σ completed tasks / observed GPU-hours. [I]
   - `successful_tasks_per_gpu_hour` = Σ successful tasks / observed GPU-hours. [I]
   - `total_throughput` = **not computable** until the user supplies T1/T2/T3, or is
     explicitly deferred (T4). [E]
4. **Idle split.** Report `cache-induced idle` plus `restore_wait`, `queue_wait`,
   `compute`, `decode`, each with an explicit measurement seam; any unmeasured term is
   `not computable`, never 0. Report the reconciliation residual against
   `cache-induced idle`. Do not use `load_back_duration_seconds` as isolated
   `restore_wait`; do not use the encoder `queue_wait_seconds` as decode-path
   `queue_wait`.
5. **Capacity matrix.** Axes/cells per §Q4 default, serialized on the single 3060
   lease, under the frozen P0-C profile; expected admission rejections are not OOM.
6. **Provenance and failure handling.** Every row binds complete server args, source/
   runtime/profile hashes, window definition, and completion set; drift ⇒ stop;
   missing ⇒ `not computable`; gains only from matched completion sets.
