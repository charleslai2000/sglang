# O001 — C6.4R storage-capacity preflight correction

The frozen C6 Qwen launch profile sets `SGLANG_HICACHE_EXTENT_BACKEND_MIN_FREE_SPACE=50GiB`. This is a **free-space watermark**, not a 50-GiB allocation requirement for the test fixture. In canonical `ExtentFileBackend`, crossing the watermark makes each write synchronously select existing LRU entries for eviction; the backend does not reject startup or writes solely because free space is below the watermark. An empty isolated root has no old entries to evict, so the earlier claim that a fixture cannot be written at 32 GiB free was too strong. It may affect retention once entries accumulate and must be evaluated against the intended minimal fixture, not treated as a hard capacity gate.

At the time of this check, `findmnt -T /mnt/data` resolved to `/dev/sda1` mounted at `/`, and `/mnt/data` was an ordinary directory consuming 2.9 GiB. No separate `/mnt/data` mount was visible in the current namespace. This observation may differ from the user's intended host/runtime and must be reconciled before choosing the storage root.

No server was launched, no new root created, and no data was deleted or modified. The C6.1 root remains preserved. Next action: confirm the execution environment exposes the expected `/mnt/data` filesystem, then use a fresh isolated root there if available. Keep the production watermark, backend, write policy, and cache semantics unchanged. Do not delete unrelated files or lower the watermark as a workaround.
