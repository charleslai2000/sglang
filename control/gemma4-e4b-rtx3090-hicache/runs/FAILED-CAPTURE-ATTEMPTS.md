# Gemma Forward capture runner corrections

The intended prefill in `/data/sglang-hicache/gemma4/runs/20261022T042401Z-forward-binding-v15/` was selected incorrectly by the prior runner contract. The live service's existing instrumentation actually emits fixed per-layer paths (`forward.layer0` … `forward.layer41`, `forward.prenorm`, `forward.finalnorm`) and logits paths keyed by RID (`forward.<RID>.extend`); it does not emit UUID-named files or Forward manifests. Raw v15 inspection showed the target request RID `d10420c4cee142bab0248a891df626ce`, exact IDs `[6974,886,2822,13315,1003,506,7217,236761]`, actual positions `[1..8]`, and matching logits. Since each subsequent Forward overwrites fixed layer paths, this is not a same-invocation proof and MUST NOT be treated as accepted numerical evidence.

The corrected source adds one opt-in UUID per actual `ForwardBatch`, carries it to layer/norm/logits artifacts, records the pinned checkpoint identity, atomically writes and refuses overwrites. The corrected selector scans the UUID-bound raw layer files and checks the target RID/input/positions, not a hypothetical pre-existing manifest. The runner verifies the model hash, writes artifacts, then validates the full one-Forward set. Scheduler Step remains optional.

`20261022T041856Z-forward-binding-v15` and `20261022T042401Z-forward-binding-v15` are failed attempts, not COMPLETE evidence: the former failed on an obsolete verifier interface; the latter used the pre-fix instrumentation. It also exposed prompt-wrapper inputs and therefore required exact validated offsets. v18 exposed that JSON manifests must be serialized as JSON rather than torch pickle. v20 passed the strict capture verifier; a separate analysis invocation initially had a wrong CLI path/RID, corrected without altering raw artifacts.
