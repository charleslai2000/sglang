Full and SWA are distinct storage/ownership pools; logical/request capacity is not their sum. SGLang runtime metrics in this run report `max_total_num_tokens=882618`, `max_total_num_tokens_swa=14353`, `max_running_requests=16`. SWA is deliberately capped by 16-request ring/window/eviction/chunk reserve; Full receives the remainder of the GPU budget. Decode CUDA Graph captured bs1,2,4,8,12,16 and startup left 1.10 GB. The 500-ms `nvidia-smi` sampler reached 23,929 MiB and 100% instantaneous utilization, with 74.8% mean across startup, workloads, shutdown. GPU returned to 1 MiB/0%; project lock released. `.94` is the highest workload-stable tested profile, not a theoretical absolute 24GB limit. `.95` allocates 17,419 more Full slots but fails its first real Prefill; `.96` fails initial forward. The workload-valid boundary is between `.94` and `.95`; no finer search was performed.

## C16×16K and C16×32K

Authoritative run used context length 65,536, max-running 16, frozen random tokens from seed 20261024, disjoint spans, Radix Cache explicitly disabled, no prefix reuse, 1 generated token/request, and SGLang default chunked prefill (2,048 chunks, 16,384 max prefill tokens). All 16 actual concurrent client requests completed each workload; each server response reports exact prompt length, `cached_tokens=0`, one generated token and `num_retractions=0`.

| workload | requests | input tokens | burst wall | aggregate prefill TPS | TTFT P50/P95 | client latency P50/P95 |
|---|---:|---:|---:|---:|---:|---:|
| C16 × 16,384 | 16/16 | 262,144 | 53.117 s | 4,935.2 | 26.11 / 49.26 s | 28.55 / 50.06 s |
| C16 × 32,767 | 16/16 | 524,272 | 128.197 s | 4,089.6 | 63.89 / 119.89 s | 68.43 / 120.43 s |

TTFT is per-request `prefill_finished_time - request_received_ts`; client latency includes queueing. P95 is nearest-rank. Runtime metrics report up to 15 running requests at once, max_running setting 16; Prefill chunking means queued requests enter in turns. At request snapshots, full/SWA active pool usage peaks were .00234/.14373; retracted count 0. This workload shows all 16 requests served, but 32K prefill is chunked rather than one 16-request monolithic batch. The `.90` and `.92` comparative runs were also successful; the no-cache `.94` run is the reportable primary result.

The `.90`, context 32,769 intermediate run rejected 32,767 inputs because its max input validator was 32,763, not because of KV capacity. Raising only context length to 65,536 accepted the same workload. No production KV math, cache ownership, or scheduler code changed.

## Distinct constraints and conclusion

- **Configuration:** arbitrary 32K total-token pool cap removed. At `.94`, actual Full/SWA physical slots are `882,618/14,353`.
- **Context/input validation:** was the cause of intermediate 32,767 rejection; context 65,536 resolved it.
- **Scheduler:** max-running 16; 2K chunk/16,384 prefill-token constraints govern per-pass work and queue delay, not pool size. All requests complete; zero retractions.
- **GPU budget:** `.94` sustained both required bursts with 23,929 MiB peak. `.95` pool allocation and Graph succeeded but first Triton Prefill OOMed; `.96` OOMed during first forward initialization. `.94` is the highest workload-stable profile; exact max allocatable slots remain between `.94` and `.95` and were not binary searched.
