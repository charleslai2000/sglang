## C16×16K and C16×32K real requests

The final successful `.94` run uses context length 65,536 (to decouple per-request input validation from KV pool sizing), max-running 16, and a fixed random corpus with disjoint prompt spans (seed 20261024). Each request generates one token, uses zero cached-prefix tokens, and all 16 return successfully with zero retractions. Full requests were submitted concurrently; normal prefill budget `max_prefill_tokens=16,384` and chunk size 2,048 stay enabled. Runtime snapshots reach 14 active requests during Prefill; remaining requests queue. Maximum scheduler setting remains 16. This is real C16 client workload, with scheduler chunking limiting each Prefill pass—not a C1 test relabeled C16.

| workload | requests | prompt tokens total | burst wall | aggregate prefill TPS | server TTFT P50/P95 | client latency P50/P95 |
|---|---:|---:|---:|---:|---:|---:|
| C16 × 16,384 | 16/16 | 262,144 | 53.549 s | 4,895.4 | 29.53 / 49.49 s | 28.50 / 50.26 s |
| C16 × 32,767 | 16/16 | 524,272 | 129.584 s | 4,045.8 | 72.62 / 121.16 s | 68.86 / 121.53 s |

TTFT is `prefill_finished_time - request_received_ts` in each raw response; end-to-end client latency includes queueing. P95 uses nearest-rank. At `.90`, repeated values were 4,910.6/4,047.0 aggregate TPS for 16K/32,767; `.92` was 4,906.8/4,042.2. The three stable memory fractions give repeatable burst throughput; no long-request OOM or retraction occurred at these operating points. `.94` samples show maximum Full/SWA occupancy about `.00674/.00842` in sampled exposed-pool metrics (the metrics exclude protected/queued logical reservations); physical GPU memory remains dominated by allocated pool capacity rather than the portion touched by this short generate-after-prefill request.

The earlier `.90`, context 32,769 run returned 400 for 32,767 input because the effective maximum input validator was 32,763 (`server.log`), not because KV allocation failed. Raising only context to 65,536 enabled the same auto-profiled pool to accept and complete 32,767, with no KV code/ownership change.

## Limits and conclusion

- **Artificial config cap:** removed. Historical 32,768 Full slots are not reported as hardware capacity.
- **Context/input limit:** independent of KV; intermediate rejection resolved via `context_length=65,536`.
- **Scheduler:** max-running 16, prefill token budget 16,384, chunks 2,048; chunking/queueing controls throughput/TTFT, not storage capacity. All 16 finish.
- **GPU:** `.94` is a stable measured point; `.96` fails on a 100 MiB real initialization allocation with 7.2 MiB free. Keep `.94` for a service profile; no code fix to KV math or Ownership was necessary.
