## Evidence and decisions

### L1/L2/L3 behavior and reclaimability

- **L1/L2: PARTIAL PASS.** Existing r61 lifecycle resume artifacts include L1 and capacity-pressure snapshots and request metrics, but the second resume reports `SOURCE_GATE_L2:0/1`; that artifact does not establish the required L2 lifecycle gate. The r60 production three-mode report (durable record in MEMORY.md, `20261121T-g1-prod-3mode-r60`) reports 1.4–2.0% hit share for L1 and 2.8–3.7% for L1+L2, alongside substantial slowdown. This is evidence of operation, not a pass of the C-8 objective.
- **L3 restore/reclaim: PASS for bounded functional evidence, not for production throughput.** Raw probe `/data/sglang-hicache/gemma4/runs/20261123T-g1-gc-probe2/` completed 400/400 (`exit.txt: bench_exit=0`; `bench.log: All requests completed`). Its manifest records the 128 MiB Extent probe configuration and source HEAD `7ea2670`. `server.log` contains L3 reads/writes, 4,651 recycle events and 1,954 Radix invalidations, with 537,102 L2-hit tokens and 1,150,645 load-back tokens in the run telemetry. No L3 degradation, backup failure, or request failure was observed in that probe. This proves bounded GC/reclaim and tier activity only; it is explicitly not the 800-request C-8 acceptance.
- CPU verification for the Extent backend at this code state: 121 passed, 1 skipped; Radix eviction tests: 2 passed (as recorded in session evidence). These support the recycle/generation/invalidation contracts, not performance.

### C-8 completeness, throughput, and capacity waits

- **C-8: NO-GO / incomplete.** Latest fixed C-8 artifacts are `/data/sglang-hicache/gemma4/runs/20261123T-g1-c8-gc-fixed-final/`. `exit.txt` records `bench_exit=124`; `bench.log` stops at 780/800 and has no final metrics summary or `perf.jsonl`. The wrapper's bounded timeout terminated it; do not infer that the remaining requests would or would not eventually finish. No valid throughput, latency, or output-correctness result exists for this attempt.
- `hashes.jsonl` has 790 input-hash records, compared against the old 800-request control's input-hash set; this confirms only that the recorded subset is drawn from the control payload set, not that all 800 completed or outputs matched.
- The C-8 server log shows continuing Extent writes/reads and recycling near shutdown (10,688 writes, 12,064 reads, 691 recycle observations; 658 Radix invalidation events). It has no observed backup failure, storage degradation, or `Request failed` before timeout. The tail nevertheless contains repeated `WAIT_CAPACITY` (`HOST_ALLOC` and `DEVICE_QUOTA`) and repeated partial allocations/retries. Recorded aggregate counts are 1,126 HOST_ALLOC and 1,567 DEVICE_QUOTA waits; summed wait durations in the run report were 50,954 s and 19,410 s respectively (overlapping request waits; not wall-clock duration). Capacity-wait improvement is **not established**.
- No server-side data demonstrates a deadlock. For example, RID `eb8c6ed079cb43bdb8b762806924036f` received successful hybrid finalize and then continued into device-capacity waiting; it had repeated read/restore and retry activity at the end. This is slow progress under saturation, not proof of permanent loss of scheduling. No production deadlock fix is justified by current evidence.
- Earlier C-8 control `/data/sglang-hicache/gemma4/runs/20261123T-g1-c8-final-candidate/` did complete 800 requests, reporting 0.33 req/s, 85.41 output tokens/s, average TTFT 84.70 s, P99 TTFT 389.34 s; however it recorded Extent reclaim failure, `kv_set_failed`, and L3 degradation. It is invalid as a healthy post-fix performance baseline. The 400/400 probe is not a substitute. Thus G4/G5 C-8 performance acceptance is **NO-GO**, not PASS.

### R60/R61 disposition

- **R60: NO-GO for G4/G5 C-8 performance.** Durable result record identifies the official 40×20 / 800-request, 8 req/s, 1024-in/256-out three-mode experiment (`20261121T-g1-prod-3mode-r60`). Reported throughput was 0.4063 req/s for L1, 0.3931 for L1+L2 (-3.25%), and 0.3575 for L1+L2+L3 (-12.01%), with output TPS 104.0/100.6/91.5. The report attributes the L3 slowdown to capacity scheduling and 6,188 DEVICE_QUOTA waits; cache hit activity is not an acceptance substitute. This is the available historical production comparison, not a healthy control for the exact post-7ea2670 C-8 build.

Resume-r2 client stderr says `SOURCE_GATE_L2:0/1`; its `cold_storage_restore.partial.json` and `frontier_recovery.partial.json` indicate incomplete phases. The untracked `run_r61_c8_guarded.sh` is a launcher script, not evidence that an R61 C-8 acceptance completed. No R61 result is promoted to PASS here.

## Remaining architectural issue

The 8 GiB Host/device cache hierarchy under a 40-client long-context workload saturates: host KV allocation and device quota become bottlenecks while demand restores and L3 reads compete with ongoing admissions. The available evidence does not establish a scheduler deadlock, and no workaround is authorized here. Resolving throughput/capacity needs a separately scoped admission/restore scheduling design and a healthy, fully completed, output-validated 800-request run against a comparable control. Until then, G4/G5 production performance remains NO-GO.
