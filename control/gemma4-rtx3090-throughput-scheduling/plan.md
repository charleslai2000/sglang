Every restore target is the request's own not-yet-computed suffix, so the L3 query is structurally unmatchable in this workload; there is no evidenced L3-side defect to fix and no restore benefit to protect, so no L3 policy change is made.

Full-tier acceptance status: 800/800 and zero Radix sanity failures, but **499.64 official TPS / 71.96% Forward duty**, below the >=540 gate. Same-window comparison of the mandatory L3 tier against the completed L1+L2 run (601.36 TPS / 80.33% duty) shows the remaining loss is CPU-side per-pass scheduling work (run_batch 64.1s, process_batch_result 23.4s, get_next_batch_to_run 16.4s of which only 0.66s is reconcile, process_input_requests 15.1s) while the device is idle 26.9%; the D2H copy needed by the mandatory L3 tier is only 1.06% of the window. `write_back` L3 correctness re-validated with the existing r15 restore oracle: eviction-driven persistence restores 1,519 tokens from L3 (`extent_read` 1024+495 keys all succeeded, `restore_success n_tokens=1519`, `hicache_prompt_tokens_total{source=l3}=1519`, zero sanity failures, identical output text/ids), while the r15 `cold → /flush_cache → restore` sequence itself does **not** restore under `write_back` because flush drops un-evicted host-dirty pages without a writeback. `write_through` therefore stays the correctness default.
