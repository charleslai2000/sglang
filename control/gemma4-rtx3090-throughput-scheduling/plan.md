This is scheduler-reported actual new Prefill work, not the logical 10.55M prompt tokens.

Actual startup log resolves T006's effective prefill limits: `chunked_prefill_size=2048`, `max_prefill_tokens=16384`, `max_running_requests=32`, `max_total_num_tokens=1443024`, context 131,072, and 1.12 GB available GPU memory at scheduler init. Thus the low 1–3 sequence Prefill batch did **not** follow from a 16K max-prefill ceiling; each new-prompt chunk was at most 2,048 tokens total (many inputs 1,024 tokens), so the configured chunk policy is a strong direct candidate cause. However, token budget alone does not show why an eligible second chunk was not admitted in every opportunity; it may be bounded by request readiness / scheduler admission ordering / restore gates. No `prefill_deny_summary` lines occur in the preserved log, despite counters and snapshot implementation in source; determine whether no deny counters were hit, the feature was not in runtime source, or logging/report period prevented emission. Logs include WAIT_CAPACITY HOST_ALLOC/FRONTIER, distinct from the 16K Prefill token ceiling. The pattern makes raising chunk size a parameter candidate but does not yet justify changing it before a time-aligned trace/ledger and controlled same-config baseline.
