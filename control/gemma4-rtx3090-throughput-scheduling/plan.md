The earlier 4096 Nsight trace's maximum 4.377s GPU gap was attributed to active no-batch scheduler polling: `sglang::schedul` spent 4.167s cumulatively in 969 `get_next_batch_to_run` calls; `recv_requests` and `process_input_requests` accounted for 0.092s and 0.010s. There was no `run_batch`/`process_batch_result`, no device kernel/copy/memset activity, and no stream/event synchronization or wait during the gap. Requests were logged in HOST_ALLOC/FRONTIER WAIT_CAPACITY; three NONE/recompute transitions appeared near the gap's end, followed by Prefill resumption. The established path is `event_loop_normal` → `get_next_batch_to_run` → `_get_new_batch_prefill_raw`/HiCache reconcile/PrefillAdder admission → no batch → `on_idle`. Existing method-level instrumentation does not split those internal phases or link one waiter to a selected batch. Thus the evidence supports scheduler no-runnable-batch polling while restores are capacity-parked, not a single blocking function or GPU stream dependency. No cache wait/ownership algorithm change was justified; only the contract-preserving chunk parameter was adopted.
