# T009 — request-row SWA ownership patch: C-8 acceptance r5/r6 and the r6 window attribution

Date: 2026-11-26. Source: `d7dc2216a3` + the uncommitted request-row SWA ownership patch
(`free_kv_row_segments`, `FreeRequestRowKV`, grouped-free ownership snapshots, streaming/PP/CPP
cleanup routing).

## 1. Why r5 was not a correctness result

`/data/sglang-hicache/gemma4/runs/20261126T-t009-c8-acceptance-r5` completed 800/800 with zero
failed requests and an exact 800-payload multiset, but it ended 800 ms before the client's
teardown with a **new** idle pool-invariant failure that the pre-patch source
(`20261126T-t009-c8-acceptance-r3`, `308e7d6b`) never produced:

```
ValueError: pool memory leak detected! [full] total=1441580, available=410426,
            evictable=1031161, protected=0, session_held=0, uncached=0
```

`available + evictable` exceeded `total` by 7, i.e. seven Full slots had been released to the
allocator while the tree still counted those tokens as evictable. r5 also drifted from the
frozen tier counters (L1 9,485,312 vs 9,533,440; newly-prefilled 1,011,201 vs 1,013,761).

Root cause (code-level, reproduced by reading the two release sites): the patch had given the
SWA component's **Branch 3** — "the entire incoming overlap lies outside the request's SWA
window" — its own `FreeDeviceKVFullOnly([value_slice[:free_end]])`. That range is *not* always
disjoint from the dead-prefix Full-only release the caller emits for the duplicate overlap
(`dead_end` split in `unified_tree_core`): when `prev_prefix_len` is inside the node and the
floor is past the node end, `dup_start < free_end`, so the same Full slots were released twice.

Fix: Branch 3 returns `prefix_len` again (the caller's duplicate-overlap release alone owns that
range), documented in place. Secondary hardening in the same commit: `free_segment` keeps the
tombstone filter (`peer_live=False`) — its call sites (node eviction, overallocated tails) are
generic, and the row-floor proof stays exclusively in `free_swa_segment(peer_live=True)`.

A regression test was attempted (`test_overlap_release_never_frees_a_full_slot_twice`, asserting
`available + evictable <= size` after the Branch-3 insert shape). It passes on both the correct
and the defective variant, so it does not discriminate this defect and was **removed** rather
than left as false assurance; the fixture does not reach the component's Branch-3 overlap with a
non-empty duplicate range.

## 3. r6 window attribution (`20261126T-t009-c8-profile-r7`)

One bounded 120 s Nsight window inside the same workload. The run itself did not complete: the
scheduler watchdog fired at 11:32:39 (300 s without progress) and the server was SIGQUIT-ed, so
**no TPS from this run is used**. The exported capture covers 11:25:13–11:27:13, i.e. the healthy
period *before* the stall (kernel span 120.06 s, 2,371,545 kernels), so the attributions below
are of the pre-stall workload. The stall's cause is not established; the window analysis is not
affected by it, and r6 (unprofiled, same tree) completed 800/800.

Host time by CUDA API in the window:

| API | calls | host time | attributed NVTX range |
|---|---|---|---|
| `cudaEventSynchronize` | 3,251 | 32.32 s | process_batch_result 15.93 s / 2,163; process_input_requests 12.90 s / 832; get_next_batch_to_run 3.50 s / 256 |
| `cudaGraphLaunch` | 2,035 | 4.41 s | run_batch |
| `cudaStreamSynchronize` | 832 | **1.82 s** | get_next_batch_to_run |
| `cub::DeviceSelect::Flagged` | 832 | – | mask filter (`swa_indices[swa_indices > 0]`) |

The patch's effect is visible directly: the mask-indexing class that dominated the pre-patch
window (1,025 calls / 14.83 s) is now 832 calls / **1.82 s** — the request-row frees no longer
pay the tombstone filter, only cache-owned node evictions do. That is consistent with the
+17.06 TPS (≈2.9%) between r3 and r6.

GPU-side picture of the same window: busy 99.72 s, gap total 20.34 s (16.9%), largest gaps
0.71 s / 0.71 s / 0.68 s (starvation bursts, matching the 264 FRONTIER waits / 89.3 s unique
wait time, 18.5 s of which overlaps idle), and ~17.8 s distributed over sub-50 ms inter-kernel
bubbles. r6's log records 688 `evt=frontier_wait` → `WAIT_CAPACITY reason=FRONTIER`, i.e. the
restore gate parks requests while an extent write is still in flight, and the pool is only ~41%
occupied at its window maximum (588,074 / 1,441,580), so the waits are durability waits, not
exhaustion.

## 4. What is left

Two distinct costs, neither of them the sync class T009 set out to remove:

1. **Inter-kernel bubbles in the eager extend path (~17.8 s / 120 s).** Launch-latency shaped:
   220 k launch API calls and 2.37 M kernels per 120 s window; decode is CUDA-graphed, prefill is
   not. Closing this needs fewer launches (extend-path graph capture or fusion), not a scheduler
   sync change.
2. **FRONTIER durability waits (688 parkings; 18.5 s idle overlap).** Requests wait for an
   in-flight L3 extent write that would make their anchor durable; the state machine already has
   a `no_material` fast-forward for the zero-expectation case, but not for "material in flight and
   the resident tail is short". Changing that is an admission decision with previously observed
   negative results in this goal (G1: higher hit share / more restore → lower throughput), so it
   requires its own measured A/B, not an assumption.
