## Convergence round (2026-11-25, second round)
Baseline fixed as the `write_back` + `wait_complete` 505.36 TPS run (`20261125T-t007-l3-writeback-repeat-c8`).

**1) Mamba test failures were not introduced by this work.** `test_unified_mamba_component_specs_use_persisted_final_hash` fails identically on a clean `06f8999484` worktree (`git worktree` at `/tmp/sglang-t007-baseline`): the test inserted 4 *tokens* and asserted 4 *pages*, so it could only pass at `page_size==1` and reported 1 (ps4) / 0 (ps64, ps128). Fixed in the test (derive `seq` from `cfg.page_size`, pass the same `seq` to the PREFETCH transfer spec): **4 passed, 15 skipped** for that selection. Full-suite comparison current-vs-clean-HEAD: 172 vs 172 failures with only a *flaky, order-dependent* `Test_FULL_SWA_ps128_sw4` subset moving between runs (the class also emits "write_back: KV subtree dropped without backup due to host memory pressure"); no failure appears only in the current tree, and the three Mamba cases plus `TestReturnedValuesDrain::test_free_values_frees_in_component_insertion_order` are fixed. No production change was involved.

**2) `_reconcile_restore_states` per-pass redundancy removed and measured.** Implemented: one `host_allocability_snapshot` per distinct pool set per reconciliation pass (scheduler-side pass scope, closed in `finally`, invalidated whenever the pass issues a retry that may claim/free host slots); a cache-side evictable-signature memo keyed by the pool generation (`_host_evictable_signature_cached`, cleared at every pass boundary and on `_reset_full`) so the walk over `evictable_host_leaves`/the whole host LRU runs once per (pool, generation) instead of once per waiter; the global generation vector memoized per pass; and the non-granted HOST_ALLOC record's fields computed only on the emit path (downstream coalescing unchanged). Nsight sub-range `scheduler.reconcile_restore_states` added with the existing `scheduler_nvtx_method` gate. Measured on the acceptance run: **0.658s / 120.06s = 0.55%** of the window, i.e. the hypothesis that this path was a throughput bottleneck is **refuted by measurement**; the change is retained as a correct, neutral removal of repeated O(host-LRU) scans (it matters when many HOST_ALLOC waiters coexist; 28 here).

**3) L3 miss/persistence/wait cost verified from the run's own evidence; no L3 change.** 445 prefetch attempts → 445 `storage_hit=0`; L2/L3 prompt tokens 0; 693 FRONTIER waits, ≈2.6ks cumulative (p50 2.9s / p90 8.7s / max 15.0s) with 288 released by the L3-only fast-forward; persistence 19.57GB = KV 8.72GB/1,064,185 keys + SWA 10.85GB/529,924 keys, i.e. KV keys = 1.05x the 1,013,761 newly-prefilled tokens (**no write amplification**). The restore target is always the request's own not-yet-computed suffix, which cannot be in L3, so 100% miss is structural, not a defect. Also restored original `_gc_evict` semantics (free space re-read per reclaimed slot) so a stale pressure reading cannot over-evict; `_select_gc_victims` keeps the linear-scan/one-sample fix. No `write_through`/`best_effort` re-experiment.

**4) Full 40×20 acceptance attempt: 800/800, 0 Sanity failures, exact 800-payload multiset — but 499.64 official TPS / 71.96% Forward duty, so the >=540 gate is NOT met.** Artifacts `/data/sglang-hicache/gemma4/runs/20261125T-t007-l3-wb-snapshot-c8/` (intent, launch argv, source identity, perf, pool series, request metrics, 120s Nsight window + analysis). Three `write_back` runs now span 499.6–522.0 TPS (≈±4%). Same-window attribution: device busy union 73.14%, idle 32.2s/120s; host-side ranges total 119.2s — `run_batch` 64.1s (of which `cudaStreamSynchronize` 48.5s is real GPU wait), `process_batch_result` 23.4s, `get_next_batch_to_run` 16.4s (reconcile only 0.66s), `process_input_requests` 15.1s; L3 D2H is 1.06% of the window. Closing the remaining ~8% requires cutting ~20s/120s of admission/result-path host work, not restore policy.

Tests: host-allocability 27 passed (incl. 4 new reuse/accuracy cases), restore-prefetch-budget + frontier-waiter-lifecycle + extent backend **160 passed, 1 skipped** (incl. new GC over-eviction guard), Mamba selection 4 passed, `git diff --check` clean, `py_compile` clean.

**4b) `write_back` validated against the existing real L3 restore case.** Two runs, both retained.
- Replaying the r15 cycle verbatim (`cold → warm → /flush_cache → same request`) under `write_back` **fails** the r15 oracle: the post-flush request goes `RESTORING → MISS_RECOMPUTE`, `cached_tokens=null`, and its logprobs equal the cold path (1.4469e-4 from warm). Cause: write_back persists a chain only when its host page is evicted, while `/flush_cache → tree_cache.reset()` drops device+host state without a writeback, so host-dirty data never reaches L3. Consistent write-back semantics, but the r15 "L3 survives flush" property belongs to `write_through` only. Artifacts `20261125T-t007-wb-l3-restore/`.
- Positive mechanism test (`20261125T-t007-wb-l3-restore2/`): cold 1,520-token target → 16 distinct 20,016-token pressure requests (evicts the target from the bounded device pool `--max-total-tokens 65536` **and** from the 1 GiB host tier) → same target again. **PASS**: `restored_cached_tokens=1519`, identical text and token ids, `extent_read keys_n=1024 succeeded_keys=1024` (8,388,608 B) + `keys_n=495 succeeded_keys=495` (4,055,040 B), `restore_success n_tokens=1519`, `hicache_prompt_tokens_total{source="l3"}=1519` with `{source="l2"}=0`, `hicache_backup_bytes_total=3.803GB`, zero sanity failures, client exit 0, GPU/lock released. Config deltas vs r15 are recorded in `launch-argv.txt`. Same r15 caveat: cold-vs-restored logprob drift 1.4469e-4 is the pre-existing cold-vs-cached path, so the oracle is the L3 read-back counters plus identical token text/ids, not logprob equality.
- Operational note from the intermediate attempts: with a 4 GiB L3 store smaller than the eviction burst, its own write-path GC keeps `ongoing_backup` non-empty for minutes so `is_fully_idle()` is false and a deferred `/flush_cache` answers "Timed out waiting for idle state"; not reproduced with a store that fits the burst (16 GiB) and not observed in the 32 GiB production-extent full-tier runs. This is capacity sizing, not a confirmed defect.

Consequence for the default policy: `write_through` remains the correctness default; `write_back` is L3-correct for eviction-driven persistence (validated above) but silently loses un-evicted host data at `/flush_cache`, which the full-tier acceptance workload never exercises.

**5) Sampled CPU attribution, and one more evidenced fix.** A 60s `py-spy` sample of the scheduler thread during the full-tier `write_back` workload showed `os.path.exists` as a 6.2% self-time leaf, all of it inside `_get_new_batch_prefill_raw` (2.54s of 41.7s sampled CPU): the operator trace-marker gates (`/tmp/t38c-durable-trace`, `/tmp/t38c-on`) were stat'ed on every call from the per-page release/revoke and drain paths (dozens of call sites). `trace_context.marker_present()` now memoizes marker presence for 1s, so an operator can still enable a trace mid-run (≤1s) while a disabled trace costs one stat per interval; `test_trace_marker_gate.py` pins the semantics (3 passed). Full-tier no-profile acceptance after the fix: **800/800, 511.58 official TPS / 72.49% duty**, zero sanity failures, exact payload multiset — i.e. +1.2% over the 505.36 baseline and still below the >=540 gate. Artifacts `20261125T-t007-l3-wb-markerfix-c8/` (60s samples in `20261125T-t007-l3-wb-pyspy-c8/`).

Remaining gap, now measured rather than inferred: the same profile puts ~6% of wall in the HiCache backup submission on the scheduler thread (`transfer_hicache_all_layer_staged_lf_pf` 2.47s + `_resolve_device_transfer_buffers` 0.65s + `alloc_writeback` 0.28s per 60s), which is the `write_back` staging launcher from the prebuilt SM86 AOT `sgl_kernel` package — a repo-side source change would not take effect in this deployment. The rest of the non-GPU time is model-path work (`gptq_marlin_gemm`/`forward` launches, `update_sliding_window_buffer` SWA metadata, `free_swa`, detokenizer sends). No further in-scope Python change is evidenced; reaching >=540 requires either an AOT transfer-launcher change or a workload/config change, neither of which is authorized here.
