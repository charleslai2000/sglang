# T009 — Eliminate Scheduler CUDA synchronization

Status: ACTIVE (measured sync removal complete and verified; the ≥600 TPS gate is not met — see Remaining)

Objective: At baseline `cb0132a6f6`, eliminate or materially reduce the two measured Scheduler sync classes—SWA mapping liveness filtering and sliding-window metadata scalar reads—without weakening slot-0/tombstone, grouped-free ownership, Full/SWA peer lifecycle, CUDA Graph metadata authority, or HiCache Host/Extent persistence/mapping semantics; achieve ≥600 official output TPS on unchanged full-tier C-8.
Inputs: Existing T007 runs and Python/Nsight attribution; upstream PRs #32701/#36723/#38159; original official C-8 workload and existing telemetry; current worktree (do not create a worktree).
Completion: Relevant allocator, grouped-free, tombstone, owner-alias and metadata tests pass; CUDA sync-debug evidence confirms targeted syncs gone/reduced; actual Gemma Owner-only FP8 GPU smoke and real L3 load-back correctness pass; original 40×20 full-tier C-8 completes 800/800 with exact payload multiset, zero sanity failures and ≥600 official output TPS. Review, commit and push the scoped implementation/final report and verify remote SHA.

Result:
Implementation (shipped candidate): `update_sliding_window_buffer` no longer reads the device prefix-sum total (`int(window_kv_indptr[-1])`) to size/slice the window KV indices. The metadata is built at fixed maximum capacity (`bs * sliding_window_size`, one `zero_()` so the translate gather cannot observe uninitialized ids) and `window_kv_indptr` alone delimits the live prefix; no consumer derives sizes from `window_kv_indices.numel()/shape`. The out-of-graph shared-pool translate in `_translate_cuda_graph_shared_pool_locs` keeps the CPU-mirror live length (`seq_lens_cpu.clamp(max=window).sum()`) and only falls back to translating the whole fixed-capacity buffer for `gpu_only` batches without a trusted mirror (tail is outside indptr and sink-zeroed, so the gather stays in bounds). No SWA free/allocator semantics were changed; no stream or event dependency was removed.

Sync evidence: the unprofiled `write_back`/`wait_complete` C-8 run at this source (`20261126T-t009-c8-acceptance-r1`, head `cb0132a6f6` + this file only) completed 800/800, zero failures, exact 800-payload multiset against both prior full-tier references, zero Radix sanity failures, **575.50 official output TPS / 88.95% forward duty** (bench 355.86 s, client wall 411 s) versus the 560.58 TPS / 365.34 s baseline at `77fd9ab9f3`: **+14.92 TPS (+2.66%)**, with TTFT p90 10.36 s (was 10.72), average ITL 0.0442 s (was 0.0454), L1=9,533,440 / newly-prefilled=1,013,761 / L2=L3=0 identical to baseline. A confirmation run is recorded separately in the frontier.

In-window attribution after the change (`20261126T-t009-sync-window-r1`, 120 s capture, `--cudabacktrace=sync:100`): **every** remaining `cudaStreamSynchronize` (1025 calls / 14.83 s host) is a `cub::DeviceSelect::Flagged`/`DeviceReduce::Sum` pair, i.e. boolean-mask indexing (`tensor[mask]` → `at::_ops::index_Tensor::call` → `nonzero_cuda_out_impl<bool>`). The scalar-read class (`at::_ops::_local_scalar_dense`) that previously dominated `run_batch` is gone. The masks are `swa_indices[swa_indices > 0]` in `SWATokenToKVPoolAllocator.free_swa`/`free_group_end` (`mem_cache/allocator/swa.py`), the required slot-0/tombstone padding filter.

Real L3 load-back correctness: `20261126T-t009-l3-restore-r4` reproduced the previously validated recipe on this source (`write_back`, context 32768, `--max-total-tokens 65536`, `--hicache-size 1`, fresh Extent, 16 × 20k-token distinct pressure requests, flush, target re-request): identical output text and token ids, **restored cached_tokens = 1519**, two `extent_read` operations (1024 + 495 keys, all succeeded). FP8 E5M2 served all of it (cold/warm/restored). r1/r2/r3 attempts at the C-8 host tier were invalid oracles: with `--hicache-size 8` the host tier is 876,989 tokens, so 10 × 46k pressure requests never overflowed it, and 22 × 46k over-evicted the target's tree node entirely; those runs recorded 0 L3 reads and are retained as evidence of oracle sizing, not defects.

Negative result (decisive, reverted): removing the padding filter via a caller "peer-live" contract at the three `SWARadixCache` eviction sites (`_evict_swa_only` internal/revived-leaf, `dec_swa_lock_only`) is **unsafe**. Run `20261126T-t009-c8-acceptance-r2` at that variant produced **494.41 TPS / 78.59% duty**, `hicache_dropped_tokens_total{reason="host_pressure"}` 108,800 (r1: 0), and SWA `backup_tokens_total` 166,413 (r1: 617,477) with 11.3 GB vs 22.1 GB of backup traffic — consistent with freeing SWA slots that a node's range no longer owns (insert-time tombstoning leaves the LRU node "live" while part of its value range maps to the padding sink), which corrupts free-list ownership and loses SWA tier state. The `> 0` filter is therefore required at every call site, and the variant was reverted (`git checkout` of the five files).

Tests: `test_swa_unittest.py`, `test_swa_lock_release_lifecycle.py`, `test_hicache_load_back_timing.py`, `test_paged_free_segment.py` — 45 passed, 18 subtests.
