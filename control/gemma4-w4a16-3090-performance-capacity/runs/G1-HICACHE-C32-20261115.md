# G1 E5M2 HiCache shared-prefix C32 follow-up — 2026-11-15

## Scope and disposition

This follow-up evaluates only the existing Gemma 4 W4A16 / BF16-compute / E5M2-KV service, with a 32-request 64K shared-prefix workload and HiCache enabled. It does not rerun BF16, GSM8K, numerical qualification, or the one-hour stability workload. Falcon cache paths were not used or changed.

**Result: C32 request completion PASS; hierarchical-cache correctness/production acceptance FAIL (NO-GO for this configuration).** This is based on a reproducible UnifiedRadixCache invariant failure after the burst, not on the user's accepted E5M2 numerical loss. The independent cause and remediation are unresolved. C32 completing all 32 HTTP requests does not erase the scheduler crash or prove safe cache reuse.

## Fixture and service

- Service: RTX 3090, model `/data/sglang-hicache/gemma4/model`, W4A16 quantized weights, BF16 compute, E5M2 KV; context 131072, max-running 32, full decode CUDA Graph max batch 32; metrics enabled; Radix enabled.
- HiCache: 2 GiB host pool; Extent file backend configured at the Gemma-only path `/data/sglang-hicache/gemma4/runs/20261115T-g1-prod-e5m2-hicache/l3-extent`, write-through, page-first, kernel I/O. No Falcon data/path was touched.
- Fixture: 32 × 65,536 tokens; common prefix 63,488 tokens, 32 distinct suffixes. Prefix SHA256 `88d98c21a57bd87e7e129289277a8e65d46474b271a36bdd828d21a83d37487e`.
- First cold warmup completed in 17.89 s with `cached_tokens=0`, as expected for a cold request. It wrote KV/SWA Extent records.

It took 60.64 s wall-clock, with ~59.97 s queue time; server logs show the restore state waited for frontier then timed out and recomputed with host survivability. Thus the apparent request-level L1 match did not imply a fast hit. At this capture, metrics showed prompt source counters L1=0, L2=0, L3=0; host backup was active (45,337 tokens and 1.064 GB accumulated bytes). The follow-up metrics after this repeat showed L1=65,535, L2=0, L3=0. There is no positive request-level proof of L2 or L3 prompt restoration.
- 32-way request driver: **32/32 requests returned successfully**, 87.26 s wall, 11.74 generated tok/s aggregate (32 output tokens each). Request artifacts are under `.../c32-l1/`.

## Failure evidence

Immediately after returning the C32 requests, the scheduler failed its idle invariant check. `unified_tree_core.py:sanity_check()` reported **11 violations across 233 nodes**, all of form “node backed up but parent not backed up”. The scheduler child exited, the supervisor shut down the service, and the port closed. This is a real runtime correctness/availability defect for this exact stress sequence. No causal attribution to the Extent backend versus concurrent Radix/HiCache write-through lifecycle is established yet.

Extent write events and `restore_backup` events occurred in the logs, proving storage I/O activity, but they do not demonstrate successful L3 request hits or a correct restore into a subsequent decode. Decode-graph max-batch configuration is not evidence that batch-32 CUDA Graph decode was actually observed; the batch driver did not persist periodic decode-batch metrics, so actual bs32 execution is **not established**. No L2/L3 transfer/recovery latency or matched output correctness was established.

## Decision and limitations

- E5M2 numerical loss is not used as a NO-GO reason here.
- L1: a repeat did report 65,535 device-cached prompt tokens; slow queue/frontier timeout and recompute make this unsuitable as a clean performance acceptance.
- L2: host backup activity is visible, but no host-source request restore was recorded.
- L3: Extent writes and restore bookkeeping events occurred, but no L3-source request restore/verified decode was recorded.
- Actual bs32 decode, layer-specific transfer throughput, successful forced L2/L3 eviction-and-restore, and recovery correctness remain unverified.
- Production deployment is not authorized by this result. Do not reuse this test directory as evidence for Falcon or another model.
