## Concrete transition candidates from source (not yet proven as the incident's first transition)

1. `UnifiedTreeCore._evict_host_leaf()` (`python/sglang/srt/mem_cache/unified_cache/unified_tree_core.py`) requires an H-leaf (no children), releases host state, unlinks it, then `_iteratively_delete_tombstone_leaf()` may delete ancestors **only while childless**. By itself this preserves tree structure.
2. `insert_host()` can extend an unbacked parent only in write-back mode; write-through drops refill under such an anchor. Its while-loop may split a matched node before inserting the suffix. A crucial caveat: the incident's violating 1-token nodes are shown with `full=yes`, whereas a split of a node with `host_value is None` produces a new prefix with no host value; that split alone cannot explain those final flags.
3. `_split_node()` creates a fresh prefix ID and preserves the existing ID for the suffix; FULL slices are split only if the old node currently has a host value. It doesn't itself clear host data on an unchanged ancestor. Tests must inspect parent, child, host slices, and pending IDs at each boundary.
4. `commit_backup()` uses `FullComponent.commit_hicache_transfer(BACKUP_HOST)`, which **unconditionally assigns** the supplied host indices to that node; it does not check current parentage/identity or whether its `BackupKV` parent still exists/has host state. `_execute_and_commit_kv_backup()` processes a captured parent-first list, but callbacks/re-entry and structural split during transfers could make later node IDs stale relative to the original chain. This is a concrete candidate worth deterministic testing, not a proven defect: establish whether operations can actually interleave in the synchronous path and whether a split changes the exact node that receives the transfer.
5. FULL host clear occurs in `FullComponent.evict_component()`; `_evict_host_leaf()` constrains it to H-leaf removal. Other direct FULL host writes are split redistribution, host insertion, and backup commit. The relevant remaining audit is operation order/reentry across those paths, especially a committed child after its parent was reclaimed or after the saved chain's shape changed.
6. `write_backup_storage()` performs synchronous gap fill through D2H backup and ACK draining and may invoke host-pool reclamation; re-entrant callbacks / node splits remain a candidate, but current evidence does not prove it caused the invariant.

The final incident reported 11 nodes with one-level sibling-pattern violations (89→88, 92→91, 95→94, 98→97, 101→100, 104→103, 107→106, 110→109, 113→112), plus 120→111 and 116→115. The exact production mode is write-through (`is_write_back=False`), so the failed parent-prefix predicate is active. The node dump makes the repeated pattern more informative: each +3 group has lengths 1536, 1, 511 (e.g. 88/89/90, 91/92/90, 94/95/93); the violating node is the 1-token middle fragment, while its 1536-token parent and 511-token sibling appear in the chain. This supports prioritizing a repeated split/insert shape, but IDs alone do not establish operation order or cause. `_split_node()` assigns a fresh ID to the new prefix fragment, retains the old ID for the suffix child, and `FullComponent.redistribute_on_node_split()` slices both FULL device and host values only when the old child has that value. Therefore a split of a host-absent child can create a fresh prefix with no `host_value`; the subsequent backup action and its node-ID list/order need a deterministic unit reproduction that checks invariant immediately after each commit. Existing split tests cover pending publication and ordinary host-only partial match but do not pin this exact repeated [1536,1,511] transition. A separate CPU probe demonstrated that adding a host child after host-leaf eligibility is sampled is rejected by `_evict_host_leaf()`'s live leaf assertion; this excludes that simplistic stale-victim hypothesis, not all reclaim/commit reentrancy.

Need separately prove whether the requested durable frontier should migrate, whether the old node remains a valid anchor, and what availability predicate remains false. Do not infer P0-B is caused by P0-A merely because they occurred in the same run.

The configured `hicache_restore_wait_timeout_s=60.0` is confirmed in startup args, but that is only the deadline. `register_frontier_waiter()`/`_wake_frontier_waiters()` and the `WAIT_CAPACITY` consumer need to be followed together. Particular source-level suspicion is a waiter keyed by a node that is split/deleted/promoted without waking/migrating the waiter, or a predicate requiring host slots while outstanding D2H/L3 bookkeeping keeps availability below demand. Neither is established yet.
