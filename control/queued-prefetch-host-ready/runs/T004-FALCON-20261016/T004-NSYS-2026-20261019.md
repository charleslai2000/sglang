## Step duration, GPU activity, and cache-to-prefill timeline
`kernel-step-ledger.json` preserves the per-step Runtime/Kernel joins and kernel intervals (not only these aggregates). It distinguishes: Scheduler/NVTX step wall; the sum of durations for all kernels launched by Runtime calls whose correlation IDs belong to that step; union of those correlation-linked device intervals; all kernel duration within the NVTX window; and union of every device kernel interval in the window. The interval union is GPU busy time evidenced by CUDA kernel activity, not a hardware utilization counter. No per-request GPU-idle attribution follows from the gaps: Nsight captured no GPU Metrics, CPU sampling, or context-switch data.

|---|---:|---:|---:|---:|---:|
| B | 281.593 | 34.526 / 34.526 | 51.025 / 48.555 | 114 / 18.339 | 5 / 1.841 |

The differing metrics are not interchangeable. Correlation-linked sums include the full device intervals tied to step-issued Runtime IDs, whereas the NVTX window is a time cut that also contains unrelated/unlinked device work. The five correlated kernels outside each Prefill step are retained in the join and not clipped/assigned into the window sum; their direction relative to the Prefill step is not established in this aggregate ledger. The Nsight CUDA Event table has 3,810 entries but every timestamp is zero, so it cannot supply event-derived per-step execution or wait durations.

A's 1,023 decode `cudaGraphLaunch` calls are actual Graph Replay launches. The matching Runtime `correlationId` expands to graph-node kernel events with graph-node IDs; e.g. iteration 19 has one graph launch, 1,238 correlated graph Kernel events, 13.153637 ms summed Kernel duration and 13.127749 ms busy union across the full graph activity. That is not A-only work: A's decode steps usually share scheduler batches with other requests, with batch size and FPM decode-request count varying. The graph's full activity interval can outlive the short Scheduler NVTX callback window; therefore the 1,023 launches cannot be reduced to the 0.722428 s union of all A-step windows (nor can their per-launch sums be claimed as A-exclusive GPU cost). A's valid statement is a 1,024-step aggregate: 5.767156 s Scheduler-step wall, 51,880 window Kernel records, 0.723338 s summed window Kernel durations, and 0.722428 s interval union across those windows; this is not a latency or an A-exclusive workload total.

Same-run monotonic clock joins to `timeline.jsonl`, `probe.jsonl`, `durable.jsonl`, and request metadata place the cache/restore path against the Prefill steps. B/C/D each had 2,048 completed KV tokens with two 1,024-page Direct-I/O KV batches (46,137,344 logical bytes each; 92,274,688 bytes / RID). The per-RID L3 operation envelopes were B/C/D 760.106 / 675.128 / 660.146 ms with recorded queue waits 34.236 / 699.842 / 1,206.977 ms; these are host service/queue observations, not GPU execution or necessarily physical-media latency. Here “enqueue → host-ready” is the monotonic delta from the request's same-run `request_enqueue` to its `ready_host` timestamp; L3 `read_envelope` begins after queued operation start and excludes the separately reported L3 queue wait. “Admission → H2D submit” is obtained from the exact `node_id + operation_id` match in `h2d_cuda_submit`; H2D bytes are 370,720,768 / 370,810,880 / 370,720,768. In this capture the exact H2D ACK occurs *during* each Prefill NVTX interval, not before it: the signed ACK-to-step-start deltas above demonstrate overlap and prohibit adding H2D event time to Prefill wall or calling that elapsed duration “GPU wait”.
