# T004 online telemetry and ownership source audit — 2026-10-18

## Boundary finding

The current dirty T004 telemetry patch carries a stable `iteration_id` in FPM (`ForwardPassMetrics`), and `scheduler.py` emits `scheduler_step_start` rows containing RIDs and step identity. Those rows include same-process monotonic/UTC timestamps, and `metrics_reporter.py` emits a separate FPM row with another calibration pair. The `run_nsys_timeline.py` analyzer expects `scheduler_step_end`, whereas the source emits `scheduler_step_forward_submit_end`; it also expects `ts_mono_ns` anchors on request events, which `_t004_timeline_log` does add. Thus RID→iteration identity exists, but event-name/schema assumptions are inconsistent and the row stamped `scheduler_step_forward_submit_end` is after Python submission, not GPU completion. A same-run analyzer must join by iteration ID and use Nsight Runtime correlation IDs/step NVTX containment; never treat submit-end as GPU completion.

The pre-fix loss/misattribution mechanism was source-derived and not reproduced at runtime in the failed T004 capture: `DeviceTimer._report()` waits for CUDA end-event readiness, so a prior interval could be retired during a later scheduler step. The former FPM callback accumulated all such callbacks into shared `_fpm_gpu_time_acc`; `_emit_forward_pass_metrics()` reset it at the step boundary and returned without publishing when it was zero. Thus a step could be omitted, and delayed time could be assigned to a later step. The current source patch removes this shared callback from FPM, preserves scheduler wall time and publishes each step identity. It avoids false per-step GPU duration and dropped identity; GPU duration must be joined from Nsight Runtime/kernel activity. Focused tests cover identity and wall time without a ready DeviceTimer result, but cannot yet be run because kernel import fails.

The last `falcon-t004-live-20261018T142208Z-nsys` artifact is not a measured T004 arm. Its `driver.stdout` shows abort at `driver.py:177` during same-run L3 fixture verification: all four storage queries had `kv_hit_pages=0` and `storage_hit_count=0`. The service log does show seed/verification `/generate` requests, then cleanup; it has no measured D/A/B/C workload. `fpm.jsonl` is empty (the collector stdout is empty), and no completed FPM rows or timeline markers establish source/send/receive/write boundaries. The generated Nsight report therefore cannot be used as target-workload GPU-step evidence.
