## 2. Runtime kernel-to-weight mapping

Evidence sources: c32 node-r2 Nsight SQLite (fixed Q6_K graph node observed 256 times, grid 8192×8, block 32×4, mean 8.143 ms); `gguf-dispatch.jsonl`; actual GGUFReader directory inventory; `gemma4_gguf.py`; `gemma4_causal.py`; `gguf.py`.

- The only Q6_K checkpoint tensors are `token_embd.weight` **[2560,262144]** and `per_layer_token_embd.weight` **[10752,262144]** in GGUF reader order; both use `block_q6_K` (256 values per 210-byte block). There are no Q6_K decoder Linear weights in the file. `gguf-dispatch.jsonl` has no `qweight_type=14` Linear entries. Thus the Q6_K MatMul is not a decoder projection and cannot be mapped to one of the Q4_0 Linear dispatch records.
- The model config path creates `embed_tokens_per_layer` as a quantized `VocabParallelEmbedding` (hidden width per layer 256 × 42 layers = 10,752). `apply_gguf_embedding()` selects token rows and invokes `ggml_dequantize`; this path alone does not explain a `mul_mat_q6_K` kernel.
- The same model ties `lm_head` to `model.embed_tokens` at TP1 (`gemma4_causal.py`), and logits computation runs through GGUF's tied qweight. Likely Q6_K source is the tied vocabulary projection; this is consistent with the measured gridX=8192 (=ceil(262144/32)) and gridY=8. This mapping is **strongly supported but not a direct per-node-to-module join**: the Nsight node table has no Linear/RID label, and dispatch aggregation omits embedding/logits. Since only the token embedding has N=262,144 and only one Q6_K node has that vocabulary-sized grid, the tied token embedding/lm-head projection is the unique matching operation. Confirm this association in a later isolated logits microprobe before changing it.
- Therefore Q6_K contributes 18.63% because the tied GGUF output projection is evaluated against a 262,144-token vocabulary for every decode step (32 BF16 rows), using the direct Q6_K MMQ kernel. Its 256 executions average 8.14ms apiece; the full graph's 2.068 s cumulative Q6_K elapsed over 254 replay windows. This is a large dense output projection, not an anomalous small decoder Linear dispatch.
- Q4_0 node kernels occur with gridX 320, 80, 64, 32, 16, 128, gridY=8. Runtime dispatch aggregates give exact c32 M=32 Linear groups, input K=2,560 and local outputs N=512,1,024,2,048,4,096,10,240 (weight shape is packed `[N,ceil(K/32)*18]`, e.g. `[10240,1440]`); these map to QKV/Column/Row parallel projections, fused `gate_up_proj`, and down projections. Representative checkpoint names: `blk.i.attn_q/k/v.weight`, `blk.i.attn_output.weight`, `blk.i.ffn_gate/up/down.weight`; fused gate/up checkpoint shards are loaded into `model.layers.i.mlp.gate_up_proj`. Layer roles vary, but shape/format mapping is exact. Nsight grid size alone cannot distinguish same-shaped individual layers.

## 3. Dispatch thresholds and actual parameters

In `python/sglang/srt/layers/quantization/gguf.py`, for non-I-matrix Q4_0/Q6_K, `mmvq_safe = 2 if qweight.shape[0] > 5120 else 6`; M≤threshold selects `ggml_mul_mat_vec_a8`, else Q4_0/K-quant in `MMQ_QUANT_TYPES` selects `ggml_mul_mat_a8`. For M=32 all measured Q4_0 Linear projections use MMQ_A8; M=1/2 Q4_0 groups (N ≤ 4,096) use MMVQ_A8, whereas M=1/2 fused gate_up N=10,240 exceeds safe 2 and therefore uses MMQ_A8. Q6_K tied vocabulary projection is shape [262144,2560] and M=32, hence MMQ_A8. The c32 report's route assertion was correct for Q4_0, but did not explicitly list the tied embedding/output projection.

A8 means BF16 activation is quantized to Q8_1 during the GEMM path; it does not mean Q4_0/Q6_K weights are converted to W4A16. Q4_0 is a 32-element block, 18 bytes (FP16 scale + 16 packed nibble bytes). Q6_K is 256 elements, 210 bytes (low/high packed codes, per-subblock scales and FP16 super-scale). Marlin W4A16 uses another packed layout/scale/group contract and cannot consume these GGUF byte streams as-is.

## 4. Mature implementations, algorithm and Gemma4 projection organization

### SGLang and llama.cpp GGUF CUDA

- This checkout's AOT `gguf_kernel.cu` is adapted from vLLM commit `755ed7b05be4743237d3339c4ff8c22bcaae04f4`; it quantizes each activation row to Q8_1 and launches the direct GGUF MMQ or MMVQ implementation. `mmq.cuh` fixes CUDA tile dimensions at `MMQ_X=4`, `MMQ_Y=32`, `NWARPS=4` for Q4_0 and Q6_K. At c32, each block covers four activation rows and 32 output rows; these choices are not the same as llama.cpp's architecture-configured generic MMQ table.
- SGLang's llama.cpp donor headers are explicitly pinned at `ce8caa6e60a03093351d6016a818720e0d46f0fb` in the neighboring `/home/ubuntu/workspaces/3rdparty/sglang` checkout (`vendor/llama_ce8caa6e/PROVENANCE.txt`). The donor CUDA algorithm uses direct block decoding and Q8_1 activation tiles. Its `mmq-config-ampere.cuh` has separate Q4_0/Q6_K cases for J values 8,16,32,64,128, `MMQ_ITER_K=256`, SRAM layouts Q8_0 for Q4_0 and Q6_K layout for Q6_K; these are Ampere dispatch/configuration choices, not evidence of a faster GA102 result. The donor's block-dot paths and current SGLang fixed tile geometry differ, but both preserve native GGUF block bytes. The llama.cpp copy under `/mnt/data/nerun-dev/llamacpp-discriminator-20260917/llama.cpp` is commit `b49650adb31f2e49a0d76113aeb1792134fd8413` (2026-09-17), not a current-mainline pin; its `mmq.cu` additionally routes NVIDIA to MMQ when FP16 MMA is unavailable or batch <64. That selection rule cannot be transplanted as a QUASAR speed claim. No comparable controlled same-GPU, same-input timing for donor versus current AOT was collected; do not infer performance from source or architecture tables.
- Current runtime `fused_mul_mat_gguf` non-I-matrix threshold remains M≤2 for N>5120, else M≤6 for MMVQ; other eligible Q4_0/Q6_K calls use MMQ. Thus c32 is MMQ_A8. A8 includes Q8_1 activation quantization. These are direct low-bit × quantized-activation algorithms, not dequantized W4A16 tensor-core paths.

### Gemma4 projections and shared KV

- Both current SGLang and the inspected vLLM `vllm/model_executor/models/gemma4.py` use a fused `QKVParallelLinear` for ordinary layers, `RowParallelLinear` for attention output, `MergedColumnParallelLinear`/`gate_up_proj` for MLP gate+up, and `RowParallelLinear` for down. Q/K/V checkpoint shards are packed into qkv; gate/up shards into gate_up. TP1 means the benchmark's N is the full projection width (the 512..10,240 dispatch groups reflect Gemma4 attention variants and MLP), while TP-sharding would alter local N.
- Gemma4's tail `num_kv_shared_layers` are structurally different: shared layers instantiate only `q_proj`, and their K/V are supplied by the last preceding non-shared layer of the same layer type. Weight mappers discard shared-layer K/V checkpoint entries. This agrees across SGLang and vLLM; it is not the per-layer `attention_k_eq_v` case (which duplicates K into V within a non-shared full-attention projection). Therefore a projection-kernel comparison should not count QKV work in those Q-only shared layers as if it were full QKV, nor infer independent KV-cache storage from parameter tensors.
- This source comparison establishes organization and intended weight mapping, not actual checkpoint dispatch/timing; the c32 `gguf-dispatch.jsonl` remains the runtime evidence for observed shapes and selected AOT routes.

### Compatibility and implications

- Repo AOT has direct GGUF Q4_0/Q6_K MMQ/MMVQ kernels and block decoders; no existing generic Triton/CUTLASS kernel accepting these byte layouts was found in inspected runtime paths. llama.cpp's direct kernels are a reference implementation, not a drop-in faster path established by evidence.
- Marlin W4A16 and generic BF16 cuBLAS require unpack/dequant/transform into a different format (or persistent transformed weights). Conversion cost, extra memory, and arithmetic/numerical behavior matter. GGUF Q4_0/Q6_K bytes cannot be passed directly as Marlin weights.
- Limited identical-input timings of current AOT MMQ/MMVQ and dequant+BF16 paths are recorded in `RESULTS-20261112.md`; no compatible alternate implementation proved faster. No current-head SGLang-vs-llama.cpp same-op benchmark was run, and no evidence justifies importing another tile schedule. A candidate design requiring a new packed cache/kernel is deferred for architecture approval.

## 5. Candidate new design (not authorized for implementation)

If the direct GGUF MMQ baseline is confirmed to leave substantial throughput unused, consider a persistent **Q6_K vocabulary-output packed-layout cache** first: at model load, transform each Q6_K block once into a decode-optimized signed-int/scale tile (or a compact int8+scale representation), then use a fused block-decode × Q8_1 activation DP4A kernel for M=32. Do not transform to Marlin W4A16; preserve Q6_K's exact block scale semantics. Potential benefit is bounded by Amdahl: eliminating all Q6_K time could reduce profiled graph's serialized cumulative kernel elapsed by at most 18.63%; graph wall improvement is lower because of overlap. Engineering cost medium/high: format transform, ~262,144×2,560/256 rows coverage, memory accounting (at least 2–4× packed-weight bytes depending target layout), persistent cache lifecycle, CUDA Graph safety, kernel correctness against ggml reference, and quality/performance A/B. Alternative Q4_0 MMQ tile scheduling for c32 dimensions is a new algorithm/dispatch tuning requiring benchmarked GA102 register/shared-memory occupancy and all-shape correctness. NCU permission denial prevents hardware-counter-guided tuning currently.

Limited same-input current-AOT measurements are documented in `RESULTS-20261112.md`; no SGLang-vs-llama.cpp kernel comparison or full c32 service A/B was performed. The proposed transformed representation/kernel still needs architecture approval and empirical validation before implementation. No production code changed.
