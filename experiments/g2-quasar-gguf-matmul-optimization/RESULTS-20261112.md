## Mature algorithm/source comparison and Gemma4 organization

As detailed in `FEASIBILITY-20261112.md`, SGLang AOT launches direct GGUF block kernels after per-row Q8_1 activation quantization; its CUDA Q4_0/Q6_K MMQ tiles are 4 output columns × 32 weight rows × 4 warps. The pinned llama.cpp donor (`ce8caa6e...`) uses direct GGUF block-dot kernels with Ampere-specific configuration tables (`J=8..128`, K iteration 256); the local llama.cpp reference tree is a different dated commit and routes NVIDIA MMQ by MMA availability/batch threshold. These are algorithm/code references only: no direct same-GPU comparison of the separate implementations was performed, so no speed ranking is asserted.

SGLang and vLLM Gemma4 sources agree on fused QKV for ordinary layers, Q-only projections for the KV-sharing tail, fused gate/up, and row-parallel O/down projections. Shared KV layers take K/V from the last preceding layer of the same attention type; their checkpoint K/V parameters are discarded. This organization explains why raw tensor inventory alone cannot define the executing Linear map. Runtime dispatch logs remain authoritative for measured Q4_0 shapes/routes.

| GGUF tensor / logical GEMM [M,N,K] | direct GGUF MMQ A8 | GGUF→BF16 dequant | BF16 GEMM after conversion | dequant BF16 result vs AOT (rel-L2; argmax) |
|---|---:|---:|---:|---|
| `blk.0.ffn_gate.weight`, Q4_0 [32,10240,2560] | 0.1990 | 0.1198 | 0.1075 | 1.77%; **different argmax** |

| same tensor, Q4_0 [2,2560,2048] | MMQ 0.0563; MMVQ 0.0578 | 0.0594 | 0.0744 | 0.67%; same argmax |
| `token_embd.weight`, Q6_K [32,262144,2560] | 8.3722 | 2.3230 | 1.6215 | 0.62%; same argmax for random probe |

Cautions: The one M=2 case has noisy/overlapping timings; MMVQ was not faster than MMQ. Direct MMQ/MVVQ same-input parity is exact for tested M=2, though separate kernel reductions can vary by ~2.4e-7. GGUF dequant+BF16-GEMM gives an approximate alternate arithmetic path, not bitwise identity: Q4_0 FFN test changes at least one output argmax. It is not acceptable as a semantic-preserving substitute without fixed activation and model-level quality acceptance.

The full materialized BF16 `token_embd` is ~1.25 GiB, versus Q6_K 550,502,400 bytes (~525 MiB); per-layer PLE embedding BF16 is ~51 MiB versus Q6_K ~21 MiB. Conversion takes ~2.32ms and subsequent [32×2560]×[2560×262144] BF16 GEMM ~1.62ms, faster than direct MMQ kernel's ~8.37ms **when the converted weight is already resident**. It is not a free kernel replacement: adds ~1.25GiB resident memory (per-layer table ~51MiB extra if also converted), conversion/startup and quality delta. No such persistent transformed cache exists or is budget-authorized here. The microbenchmark thus quantifies a promising but semantically non-identical and memory-costly alternate path, not a production win.

## Disposition / proposal

No compatible existing route demonstrates a safe direct optimization: current repo has direct GGUF MMQ and MMVQ; the public llama.cpp CUDA implementation also directly decodes GGUF formats and is not a proven faster drop-in for this ABI/shape. W4A16 Marlin is a different packed format and cannot consume raw GGUF bytes.

An **architecture decision is required** before a persistent transformed-weight path or new kernel. Recommended candidate for a small follow-up prototype: a decode-only cache/representation for the 262,144-token Q6_K tied output projection. Upper bound from measured cumulative kernel share is 18.63% of the node elapsed denominator; actual graph wall gain will be smaller due to overlap and A8/dispatch costs. Engineering cost medium/high: preserve Q6_K scale semantics, implement format conversion plus optimized tiled DP4A or other supported primitive, memory admission/eviction, checkpoint/shard/load lifecycle, CUDA Graph safety, correctness against direct AOT, fixed-token/logits/quality validation, and matched c32 A/B. A BF16 full-head copy is the simplest feasibility bound (~1.25 GiB extra and ~2.32ms conversion), but random-probe parity is only rel-L2 0.62%; the Q4_0 FFN probe changed argmax, so this arithmetic path cannot be presumed quality-neutral.

No production source change, full profile, or service benchmark was made. GPU returned to 1MiB/0%, no profile service port remains bound, and the project lock is available.
