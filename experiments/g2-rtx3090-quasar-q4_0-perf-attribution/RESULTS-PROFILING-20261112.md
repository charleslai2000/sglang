# QUASAR Q4_0 RTX3090 profiling attribution — 2026-11-12

## Existing measurement stack and evidence

This work reuses the completed Gemma Radix Profiler, not a replacement framework:

- `python/sglang/srt/utils/nvtx_utils.py` emits `RADIX8K_FWD` scopes with scheduler step, mode, actual batch, Graph bucket and RID set.
- `python/sglang/srt/managers/scheduler.py` handles SIGUSR1/SIGUSR2 in the CUDA-owning Scheduler and brackets CUPTI capture with `cudaProfilerStart/Stop`.
- `python/sglang/srt/utils/device_timer.py` records CUDA Event duration by RID/category/batch. `metrics_reporter.py` accumulates event time per logging window; its `fwd occupancy = accumulated CUDA Event duration / CPU wall-window` is a timing duty ratio, **not SM occupancy**.
- Existing collector/client: `control/gemma4-e4b-rtx3090-radix-8k-profiler/runs/launch_profiled_radix8k.sh`, `profile_window_client.py`; existing graph join: `control/gemma4-e4b-rtx3090-g1-perf-convergence/runs/analyze_same_run_graph_timeline.py` (NVTX thread → runtime `cudaGraphLaunch` correlationId → CUPTI `GRAPH_TRACE`).
- Historical diagnosis: `control/gemma4-e4b-rtx3090-radix-8k-profiler/runs/GEMMA4-RADIX-8K-PROFILER-DIAGNOSTIC-20261031.md`. It measured W4A16 c16 batch-2 Prefill kernels and c16/c24/c32 Graph replay; NCU counters were denied with `ERR_NVGPUCTRPERM`.

QUASAR Run4 (`/data/sglang-hicache/g2-quasar-runs/20261111T-g2-quasar-radix8k-prefix-e5m2-run4`) contains 7,244 RID-tagged forward Event records, all 348 completed request records, exact c1/c8/c32 Prefix-Hit Extend and c32 Decode batches, plus 200ms NVML samples. It has no Nsight trace, per-Linear dispatch file, SM/DRAM counters or warp-stall counters. Baseline: c1 Extend 907–911ms; c8 one-request Extend about 932–935ms and seven-request Extend 6,548–6,577ms; c32 Decode Event TPS 699.769–700.784. These are forward-level timings, not per-kernel attribution. Full setup and historical comparability limits remain in `experiments/g2-quasar-radix8k-prefix-benchmark/RESULTS-20261111.md`.

## New QUASAR c8 target Prefill trace

Run: `/data/sglang-hicache/g2-quasar-runs/20261112T-g2-quasar-q4-profile-prefill-c8-r2/`; profile artifact `profile.nsys-rep`, export `profile.sqlite`; model SHA is the Run4 QUASAR identity, BF16 compute/E5M2 KV, TP1 Triton, Prefill CUDA Graph disabled, Full Decode Graph enabled. The accepted target c8 cohort completed all 8 requests × 256 outputs, device cache hit 7,168 with Host hit 0. The trace has exact target `RADIX8K_FWD` RIDs and 2,048-token Prefill forwards: one batch-1 Extend plus one batch-7 Extend. NVTX and GPU kernel intervals were directly inspected in the exported SQLite. This reuses the existing NVTX/CUPTI infrastructure and is a targeted capture; startup/warmup data is not included in target sums.

| Target forward | actual batch / RIDs | NVTX span | sum of contained CUDA kernel durations |
|---|---:|---:|---:|
| c8 first Extend | 1 / 1 | 328.108ms | 324.219ms |
| c8 second Extend | 7 / 7 | 2,308.335ms | 2,303.780ms |

The dominant CUDA kernel is the current fork's Q4_0 A8 matrix multiply `mul_mat_q4_0<c10::BFloat16, false>`: batch-1 Extend 290.837ms/778 events; batch-7 Extend 2,092.275ms/772 events. Next is attention `_fwd_kernel`: 21.258ms/15 events and 131.636ms/15 events, respectively. Explicit `quantize_q8_1<c10::BFloat16>` activation conversion costs 3.917ms/108 events and 26.869ms/108 events. Remaining grouped kernels include Cat 1.768/12.409ms, activation 1.147/7.803ms and RMSNorm about 0.694/5.312ms. Values are accumulated kernel elapsed durations; kernels may overlap and should not be added as wall time. Graph is off for these two Extend steps. This is actual QUASAR trace evidence, unlike the historical Marlin profile.

Within the summed Extend kernel durations, Q4_0 matmul is ~89.7% (batch1) and ~90.8% (batch7); Q8_1 input quantization ~1.2% in each. This shows the present dominant measured cost is the Q4_0 matmul path, not the activation quantizer or obvious dispatch to generic dequant GEMM. It does not by itself establish whether MMQ/MMVQ is optimally configured or justify changing the kernel.

The same c8 profile naturally contains 256 actual Decode Graph replay joins (batch=8, graph=1, bucket=8), each joined uniquely by the existing same-thread runtime correlationId method. Graph replay duration median/mean/P95: 15.034/15.054/15.151ms. This is a useful c8 profile cross-check but not the requested QUASAR batch32 attribution. The profiling run's client file records exact Prefix-Hit and output counts but does not persist output IDs, so it is not a bitwise greedy-ID equivalence proof to Run4.

## c32 Decode trace and hardware counters

A valid c32 collection is available at `/data/sglang-hicache/g2-quasar-runs/20261112T-g2-quasar-q4-profile-decode-c32-r1/`. It contains 32 completed requests × 256 outputs; all responses report 7,168 device-prefix cache tokens and zero host tokens, and all 32 output-ID hashes match the corresponding Run4 c32 round-1 IDs after exact RID normalization. The server log independently records sustained `Decode batch, #running-req: 32, cuda graph: True` (steady reported throughput about 689–696 tokens/s). Nsight exported 256 batch32 `RADIX8K_FWD` ranges and 256 unique `cudaGraphLaunch` correlationId → `GRAPH_TRACE` joins. The graph-level replay durations are about 42.7–44.3 ms per step in this profiled run; they are not directly interchangeable with Run4 CUDA Event TPS.

**Node attribution is now available from the corrected node-granularity run** at `/data/sglang-hicache/g2-quasar-runs/20261112T-g2-quasar-q4-profile-decode-c32-node-r2/` (`nsys.nsys-rep`, `nsys.sqlite`). `--cuda-graph-trace=node` exports `CUDA_GRAPH_NODE_EVENTS` and `CUPTI_ACTIVITY_KIND_KERNEL.graphNodeId`; the earlier node-r1 file had only startup/invalid cache setup and is excluded. Run2 used the same model/runtime, one 7,168-token primer, 8K validation (`cached=7168`, device=7168, host=0), and 32 complete requests. All 32 had 256 outputs, device prefix hit 7,168/host 0 and output-ID hashes matching Run4 round1. Scheduler logs show sustained batch32 `cuda graph: True`; steady server throughput in the profiled run is 753–759 tok/s. There are 256 batch32 NVTX replay ranges and 256 unique API correlationId matches; node events pair the GPU work with each graph replay. Summing device Kernel elapsed durations over 254 stable replay windows (excluding two windows with incomplete boundary capture), the mean graph-node kernel count is 1,494 and mean execution envelope ~48.7ms. Kernel duration shares (overlapped elapsed-time denominator, not wall time): Q4_0 `mul_mat_q4_0<c10::BFloat16,false>` **6,633.978 ms / 59.77%**; FlashInfer/Triton grouped decode attention `_fwd_grouped_kernel_stage1` plus `_fwd_kernel_stage2` **1,582.135 ms / 14.25%**; Q6_K matmul **2,068.343 ms / 18.63%**; Q8_1 quantization **149.534 ms / 1.35%**; remaining kernels **651.700 ms / 5.87%**. These totals cover 254 stable × 32-request decode replays; summed kernel durations overlap and do not add to replay wall duration. The main measured kernel hotspot is real Q4_0 MMQ, but no inefficiency/defect is established merely by its share.

The first c32 valid graph-granularity run's whole-capture `cuda_gpu_kern_sum` reports Q4_0 MatMul 26.672 s (90.1%), `_fwd_kernel` 1.876 s (6.3%), Q8_1 quantize 0.311 s (1.1%) over 1,032/168/1,036 instances respectively; these include 32 concurrent Extends and are not Decode-node fractions. The corrected node run supersedes the previous unknown node-share status.

Runtime GGUF dispatch telemetry for the valid c32 run includes 648 Linear dispatch aggregates and reports `mmq_a8`/`mmvq_a8` with qweight type 2 (Q4_0) for batch-32/batch-16/... and token-batch shapes; this establishes real Q4_0 routes but is not a per-node replay attribution. Existing `gguf.py` selects MMVQ A8 for small `M` (batch32 decode uses the measured MMQ_A8 branch according to the telemetry); no route mismatch or configuration defect is evident. c8 Prefill already establishes Q4_0 MatMul as the major measured Extend cost (~89.7–90.8% of contained kernel elapsed), but does not transfer to Decode.

A focused NCU counter availability query (`/opt/nvidia/nsight-compute/2025.2.1/ncu --query-metrics ...`) returns **`ERR_NVGPUCTRPERM`** on the RTX 3090. No permission change was attempted. Therefore SM active, DRAM throughput, compute-unit utilization, and warp-stall evidence are unavailable. No confirmed defect or low-risk fix is established; no code repair/A-B is justified. The c8 DeviceTimer vs NVTX differential is still **UNKNOWN**: c8 Run4 CUDA Events are 931.523 ms/6,548.114 ms, while the separate Nsight run's full Extend NVTX spans are 328.108/2,308.335 ms. The source shows the EagerRunner's DeviceTimer boundary is inside `eager_runner.execute`, while the ModelRunner NVTX wraps the call outside it; that supports a scope difference but the two measurements are from separate runs and do not exactly decompose GPU kernels, idle gaps, CPU submission/wait or non-kernel work. No same-run paired collection was made.

The corrected node-granularity run supersedes the earlier statement that Nsight/CUPTI did not expose GraphNode IDs: it exposes node events and kernel graphNodeId, enabling the completed c32 node attribution above. The ~48.7ms mean node-event envelope and 753–759 scheduler tokens/s are not yet reconciled to a common time window/denominator; they must not be treated as direct reciprocals or as a validated throughput identity. See `experiments/g2-quasar-gguf-matmul-optimization/FEASIBILITY-20261112.md` for exact interpretation and the Q6_K mapping caveat. GPU service/agent were stopped; final check: 1 MiB GPU memory, 0% utilization, port 31382 clear, exclusive lock available. Failed/invalid collection evidence is retained under the run directories and excluded above.
